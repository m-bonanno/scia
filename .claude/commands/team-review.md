---
description: Review a pull request with the team of roles, post each review on the PR, and merge it when the team approves.
---

Review PR `$ARGUMENTS` (default: the PR of the current branch) as `docs/development/review-flow.md` describes — that runbook is the rule, this is the order of the steps.

1. Check out the PR's branch; make sure it is pushed and the working tree is clean, and that the PR carries its labels and its assignee, as `git-flow.md` gives them ("A pull request", 5 and 6; "The two PRs that have no issue"): add what is missing before the review. **A PR from a fork is never checked out with the hooks on, and nothing of it is run**: fetch `pull/<N>/head` and read it as `review-flow.md`, "A pull request from outside", says — the gates are CI's.
2. Decide the roles from the files the PR changes, from what it releases and from its size (the table in the runbook, and "A small PR is the tech lead's alone"). The tech lead always reviews. In a later round, decide them again on the whole diff, as the runbook says — but for a fix that touches only specs or the PR body, which the roles that blocked review alone (#187).
3. Start **one reviewer per role, in parallel, each with a fresh context**: give it its role file (`.claude/agents/<role>.md`), the PR number and the issue it closes — nothing of your own reasoning. Each writes its review to a file outside the repository, in a folder of its own (one file per round), is told not to read the other roles' folders, and answers with the verdict and its blocking findings only. Tell each whether the PR comes from a fork: a reviewer of a fork's PR runs nothing of it (`review-flow.md`, "A pull request from outside"). Tell each that a mutant or a probe runs in a worktree of its own (`git worktree add --detach <dir> <head>`), never in the checkout the other roles read and run specs in (`.claude/gotchas.md`, "Specs", #144). In a later round, resume the agents of the roles the runbook says review again — not every role — so that each checks its own findings.
4. Post each file on the PR as a comment, under the role's header (`## Tech lead review`, `## Backend review`, …), exactly as written.
5. If the tech lead's review of a small PR calls a role in, start that role now, in the same round, and post its review too. If two or more roles have findings, have the tech lead write the synthesis and post it.
6. Mend the body where a role noted it (`Body:`, `review-flow.md`, "What is blocking"), then close the round with the `## Team verdict` comment: the verdict, the head commit it holds for, each role's answer, what was mended in the body, and the follow-up issue where the runbook asks for one. For a PR from a fork, post the verdict on its linked issue too, with each blocking finding on a line.
7. If the verdict is "changes requested": fix on the same branch (new commits, never a force-push), push, mend the PR body where the fix changes what it says, and go back to step 2. A PR from a fork is fixed by its author: the next round starts when they have pushed and the owner asks for it.
8. When the team approves the head commit **and** CI is green on it, merge as the runbook says for that kind of PR. After a merge of `develop` into the approved branch, run `npm run check:merge` and do as `review-flow.md`, "Rules", says. Never merge a PR into `main` without the owner's word. A PR opened from the owner's account is merged with `gh pr merge --admin` (the owner's approval cannot be recorded on it). A squash is given its own body, `--body "Closes #N"`, plus the `BREAKING CHANGE:` footer for a breaking change and the line `This reverts commit <sha>.` for a revert: GitHub would write every commit of the branch into it, and the release notes list each issue it names (#249). A PR anyone else opened waits until the owner has approved it on GitHub, and is then merged without `--admin`: never approve it for them, and never `--admin` it, which would merge it with no approval. A PR from a fork also waits for the owner to take CodeQL's three checks off `develop`'s protection by hand, since none runs on it; nothing else is merged into `develop` until they are back, and after the merge the protection is read back with nine contexts (`gh api repos/<owner>/<repo>/branches/develop/protection/required_status_checks`; `git-flow.md`, "Repository settings"). Every merge is read back (`gh pr view <n> --json state` answers `MERGED`) before step 9 touches a branch.
9. After the merge of a work branch: delete it on GitHub (the repository no longer does: `git push origin --delete <branch>`), pull the base branch and delete the local branch. Never delete the head of a release or of its back-merge: they are `develop` and `main`.
10. After every merge into `develop` or `main`, read that a Release run started for the merge commit (`gh run list --workflow Release --commit <merge sha>`). GitHub once recorded no push for a merge, and started nothing (#95). When none has started a minute after the merge, start it: `gh workflow run release.yml --ref <develop|main>`, with no `installer_tag`. A `main` it is for is a release the owner already said yes to. The Release watch does the same for `develop` every three hours, and never for `main` (`release-flow.md`).
