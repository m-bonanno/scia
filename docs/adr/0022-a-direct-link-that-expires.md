# ADR 0022 — A direct link that expires is asked for again by the manager, keeping the bytes

- **Status**: accepted
- **Date**: 2026-11-23

## Context

A direct link a debrid service gives does not last ([ADR 0005](./0005-a-service-resolves-a-link.md), point 4). The link is kept and used again after a pause or a restart, so that the service is asked once; a long download, or one paused for long enough, outlives it. Until now its host's refusal failed the download, and "Retry" asked for a new link, keeping the bytes only if the new link was the same file. #7 asks for more: a link that expires during a long download is unlocked again without losing the bytes on the disk (#180).

ADR 0001 foresaw "a `RemoteSource` decorator that re-resolves an expired link"; ADR 0005 left to this item where the step goes. AllDebrid's documentation says neither how long a direct link lasts nor how its host answers once it has expired, and it names no code of its own for an expired link.

## Decision

1. **The manager asks again, not a decorator of `RemoteSource`.** The new link has to be kept in the record (`unlockedUrl`), and the new file compared with the one the bytes on the disk are of — what ADR 0005 already gives the manager for the first link (point 3, Alternatives). `DownloadManager.#runFile` runs a file's task; when the task fails because its link expired, the manager keeps its progress, asks the service again through the same step (`#address`), asks the new link's host what the file is, and runs a new task on it from the segments kept. A link kept from before the run — a pause, a restart — that answers as expired when it is first asked (`#locate`) is asked for again the same way.
2. **Expired is a 403 or a 410 from the host of a direct link a service gave** (`EXPIRED`), **or a web page that is not the file whose bytes are kept** (`NotTheFile`: at the probe, point 5) — and only of such a link: a direct link pasted as it stands still fails at once on a 403, as every host does (`apps/server/CLAUDE.md`, "Retry what can heal"). No code of the service is taken: AllDebrid documents none for an expired direct link. The service is not asked what it thinks of the old link: it is simply asked for a new one, and its refusal then — the file gone from the hoster, an account no longer premium — fails the download in its words, as at the first unlock.
3. **Asked again only for a link that brought bytes the download keeps.** A link that expires after bytes came through it is asked for again — unless the download had started again from the first byte on it: a link given again that turned out to be another file, or whose host serves no ranges, keeps nothing of what came before, and is the last link asked for in that run. A link that is refused before its first byte — the first one the service gives, or a new one — fails the download with what its host answered. Each request can count against what the account is allowed of a host, and a file that outlives every link, or a service whose links are refused at once, would otherwise have the service asked without end. "Retry" asks again, as before.
4. **The new link is checked to be the same file**, as any host's file is checked between two runs (`#adopt`): the same size, and the same validator where both answers carry one. A different file is a changed file, as it is today: the bytes on the disk are of another file, and the download starts again from the first byte of the new one.
5. **A web page is never saved over the bytes of a service's link.** A page from a service's direct link is not the file when the download keeps bytes (`downloadedBytes > 0`) and the page is not the file those bytes are of: its size differs, or its validator does where both answers carry one — the test `#adopt` makes of a changed file (`isAnotherFile`). Such a page from a kept link is asked for again (point 3); from a new link it fails the download as `HTTP_STATUS` with no status: the row then says the link the service gave no longer works, and that "Retry" asks for a new one — which is true, and is the remedy. A page with no bytes kept — the first link of a download — is what the service unlocked, and is downloaded as before: the file may be a page. And a page that is the file whose bytes are kept — a host that labels the file `text/html` — goes on from them, after an expiry, a pause, a restart or a "Retry". No code says "a page" today; one would need words of its own for a remedy that is the same.
6. **The log says that a link was asked for again** (`link_unlocked_again`, with the download's id) — never the link.

## Alternatives considered

- **A `RemoteSource` decorator that unlocks again inside `open`.** Rejected: it would hide from the manager the link it has to keep in the state, and a different file could not be started again from inside a task whose segments were planned for the old one. Its one advantage — the connections of a task going on without stopping — is worth less than a pause of a second at each expiry.
- **Asking the service again at every refusal of the direct link.** Rejected: point 3. A 404 or a 5xx of a direct link is not taken for an expiry either: the first says the file is not there, which a new link of the same service would most likely say too; the second heals by itself, and is retried as every host's.
- **Asking again once for each link that brought bytes, whatever was kept.** The first form of this decision. Rejected in review: a link on which the download starts from the first byte brings bytes too, and a file that outlives every link was asked for without end, with nothing kept.
- **Asking again on a timer, before the link expires.** Rejected: the service does not say how long a link lasts, and every request may count against the account.
- **Failing a different file instead of starting it again.** Rejected: "Retry" would start it again all the same, and that is what a changed file does today. The person loses the bytes either way; a failure would only add a press.
- **Saving a page from a service's link as the file**, as before this decision, also for a download that already had its file. Rejected: the row read Completed over a web page under the film's name, and the bytes the download had were gone — the outcome `apps/server/CLAUDE.md` says a link is never started to risk.
- **Taking every page from a service's link for an expired link, the first one included.** Rejected: the file a service unlocks may itself be a page, and a page from a first link that is an expiry has no bytes to lose — the person sees what was saved, and the specs of ADR 0009 hold that such a link is downloaded and never read for a video.
- **Taking a page for "not the file" whenever the download's file is named.** The second form of point 5. Rejected in review: "Retry" clears the kept link but not the name, so a file that is a page — or a host that labels its files `text/html` — failed again at every "Retry", and at every pause, while the row promised that "Retry" would mend it.

## Consequences

- A long download through a service goes on by itself after its link expires, with the bytes it had; the person sees a pause of the speed, and no failure.
- A different file behind the new link starts again from its first byte without a word on the row; the log says the link was asked for again. If that new link expires too, the download fails and "Retry" asks again.
- What a real AllDebrid host answers once a link has expired is not known: the specs hold the two statuses the issue names (#180) and a web page. A host that answers otherwise is treated as before: a 404 fails the download, and "Retry" asks for a new link; a 200 whose body is something other than a page — a code of the service written as JSON, say — at the probe of a link kept over a pause or a restart is taken for a changed file, and downloaded as the file. Seeing the real service (#7's checklist) would tell whether more is needed.
- A page met in the middle of a task — a 200 to a range — is "the host ignored the range", as before: it fails the download (`HTTP_STATUS`, 200), and is not asked for again.
- A file that is a web page, unlocked by a service, downloads, and goes on from its bytes after an expiry, a pause, a restart or a "Retry", as long as its host answers the same size and validator.
- A page that happens to have the size and validator of the file whose bytes are kept is taken for that file. A host gives no other sign; an expiry page as large as the file, with the file's ETag, is not a case anyone has seen.
- A first link that answers the service's page for an expired or broken link is saved as the file, as before: no bytes are lost, and the row reads Completed over a page.
- A host whose two links of one file carry different validators (two servers of the service, each with its own ETag) is taken for a different file: the download starts again, and fails if that link expires too.
- A download on one connection — a host that does not serve ranges — starts again from its first byte on the new link, as it does after any cut, and fails if that link expires too.
