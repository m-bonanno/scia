# ADR 0023 — A key is said kept once what opens it is on disk, and a key that cannot be read back is said

- **Status**: accepted
- **Date**: 2026-11-23

## Context

[ADR 0004](./0004-the-key-of-a-service.md) keeps the key of a connected service sealed by Electron's `safeStorage`. On Windows that seal is made with a key of Chromium's, which the Data Protection API seals for the person's account and Chromium keeps in the profile's `Local State` (`os_crypt.encrypted_key`).

A run of the real app on Windows (review of #65, 20 November 2026) connected AllDebrid on a scratch profile and killed the app (`taskkill /T /F`) about seven seconds later. At the next start main could not open the key ("Error while decrypting the ciphertext provided to safeStorage.decryptString"), the engine started with no service, Settings said "Not connected" as if nothing had happened, and a hoster link added next was fetched as it stands — for a real hoster, its page saved as the file, which [ADR 0005](./0005-a-service-resolves-a-link.md), point 6, exists to prevent. With fifteen seconds between the connection and the kill, the key was read back (#69).

What explains both runs: Chromium makes its sealing key at the first use of `safeStorage` — Scia's first was the connection — and writes `Local State` some seconds after a change, not at once; a kill before that write leaves a key sealed with a key nobody kept, and the next start makes another. **Measured** in CI on the built app (E2E (Windows), run 45149710018, job 137607737273, head `55ca2fe`): on a new profile the sealing key reached `Local State` 10.4 s after the launch; in each of three runs that connected at once, the key was sealed before it was on disk, and the write waited 9.1 s for it (`key_kept { sealOnDisk: false, waitedMs: 9111 | 9122 | 9070 }`, about 10 s after `key_seal_prepared`) — so each of the kills that followed would have fallen inside the window of #69 without the wait. Whether the key was made by `prepare` or by Chromium at its own start is not isolated: no run went without `prepare`. Electron has no call that writes `Local State` now. The owner decided (21 November 2026) that `v1.0.0` waits for the fix.

## Decision

1. **Main answers that a key is kept only once what opens it is on disk.** After the sealed key is written, main reads the profile's `Local State` until it holds `os_crypt.encrypted_key` (`holdsSealingKey`), every 250 ms and for `KEY_SEAL_LIMIT_MS` (20 s, in `@scia/contracts`) at most. Seen once, it is not looked for again in that run: Chromium does not take it away. Past the limit the write is refused, and the engine undoes it as any refused write ([ADR 0004](./0004-the-key-of-a-service.md), point 6): Settings says the key was not kept, and nothing is connected. **Where the system's keychain or keyring keeps the sealing key** (`SEALING_KEY_IN_LOCAL_STATE` in `key-store.ts`: every system but Windows), it has it the moment it is made, and nothing is waited for.
2. **Main has the system make its sealing key at the start, when `Local State` does not hold it yet** (`KeyVault.prepare`: an empty string sealed and thrown away), before the engine starts. It reaches the disk seconds later, long before a person usually connects a service; a connection in the first seconds of a new profile waits for it. Where nothing seals, and where the key is already on disk, nothing is asked of the system — on Linux, no keyring is opened for a person who never connects a service. A refusal never fails the start: a line in the log.
3. **The engine waits for main's answer to a write `KEY_SEAL_LIMIT_MS` beyond its five seconds** (`ParentVault`); a read and a removal keep five seconds.
4. **A key that was kept and cannot be read back at a start is said.** `GET /integrations` carries `keyNotRead` for each service, and Settings says "Scia could not read back the key it kept for AllDebrid. Connect it again." under the row's head, with the ways to connect above it. It is said until a key is connected again, or the service is disconnected — Settings offers its "Disconnect" beside the sentence while no way to connect is open, the way out for a person who will not connect again. It covers the system that cannot open the key and the main that did not answer within five seconds alike: both leave Scia with no key it had kept. This replaces ADR 0004's consequence in which such a start showed "Not connected" and said nothing more.
5. **While a kept key cannot be read, a link of the account's hosts is not fetched as it stands.** The list the account gave in an earlier run is still kept ([ADR 0005](./0005-a-service-resolves-a-link.md), point 5), and a link on one of its domains or their `www.` fails `SERVICE_NEEDED` before anything is fetched — also when the public list of [ADR 0006](./0006-a-file-host-without-a-service.md) cannot be read; otherwise the public list decides, as with no service connected. Not the account's rule for subdomains: no service can unlock the link now, and the other names of a host are the servers of its files, which give them to anyone (ADR 0006, point 3). With no key kept, a list left behind decides nothing.
6. **The log says what was on disk, and when**: `key_seal_prepared` at a start that made the sealing key, and `key_kept` with `sealOnDisk` (at the write) and `waitedMs` for every write. Never the key.

## Alternatives considered

- **Have Chromium write `Local State` at once.** Electron exposes no call for it: the file is written on Chromium's timer and at a quit, and a kill is no quit.
- **Check that the sealed key opens with what is on disk**: read `os_crypt.encrypted_key`, open it with the Data Protection API through koffi, and the sealed key with AES-GCM in Node. Rejected: it rebuilds Chromium's format, which changes between versions, and gives the app's one native module a second road ([ADR 0020](./0020-the-window-in-use-asked-of-windows.md)) — for what the presence of the key on disk says on a profile Scia made.
- **Seal with the Data Protection API directly, through koffi**, with no key of Chromium's in between. Rejected for now: a road that exists on Windows alone, against ADR 0004's choice of `safeStorage`; it would be the change if the file ever proves unreliable.
- **Wait for the key on disk, and make it only at the first connection.** Every first connection of a profile would wait for Chromium's timer, seconds of "Checking…".
- **Say nothing until the key can be read, and leave the start as it was.** A person told "Not connected" with no reason, and a hoster's page saved as the file meanwhile: the two things #69 asks to end.

## Consequences

- A key the person was told is connected is read back however soon after the app is killed — held by specs, and proven by the E2E suite, which kills the built app (`taskkill /T /F`) right after a connection on three new profiles, in CI, and read each key back (run 45149710018; [`apps/desktop/e2e/keys.e2e.test.ts`](../../apps/desktop/e2e/keys.e2e.test.ts)). Not by a hand on this machine, nor with the packaged app.
- Main reads a file Chromium renames onto: while a write waits, every 250 ms, and once at a start. On Windows a read that meets the rename can make it fail (`.claude/gotchas.md`, Specs, #137); Chromium writes the file again at its next change. How often that happens is not measured.
- A profile whose `Local State` holds a sealing key the system cannot open — copied from another account — has a key on disk, and the write does not wait. Whether Chromium then makes a new key, and when it writes it, is not measured: such a profile can still lose a key connected and killed within seconds. It starts with `keyNotRead`, said, and connects again.
- The first seconds of a new profile: a connection waits until Chromium has written the file — about 9 s for one made at once in CI, 10 s from the launch to the key on disk. `KEY_SEAL_LIMIT_MS` is twice that. The E2E suite prints both at every run.
- Linux is untried, as the rest of Scia there.
