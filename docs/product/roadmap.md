# Scia — roadmap

The state is the real one: an item is "done" only if it was verified in the real app.

## M0 — Foundations (done, but for what its lines name as not tried or not seen)

- Monorepo, tooling, hooks, tests on four layers.
- Repository on GitHub with GitFlow, checks on PRs on Ubuntu and on Windows ([ADR 0008](../adr/0008-the-delivery-pipeline.md)) — from #90 on, the workflow runs them again on the commit a merge makes, before it is released — seen on the merge of #94, whose gates ran green on both systems before semantic-release, which found nothing to release; a red merged commit, which is to make no tag, has not happened yet — automatic versions and release notes (semantic-release). The Windows installer came out of CI on request three times (`v1.0.0-beta.10` to `.12`); from `v1.0.0-beta.13` on, the workflow builds it for every release, beta or stable, with the files an updater reads (#83) — `.13`'s run itself dispatched by hand, because GitHub recorded no push for the merge of #86 (#95). Two built by CI were installed and run: `v1.0.0-beta.10`, and `v1.0.0-beta.12` on a scratch profile, its log read (#78). Both were installed silently from the command line (#78): none has been installed by hand from a download, where SmartScreen asks first, nor on a clean machine (M1, below). An installer run over an installed Scia was tried twice (#82), neither time by hand from a download: through the updater, from a local build of its branch to `v1.0.0-beta.13`'s installer, with the app run afterwards as `1.0.0-beta.13`; and from the command line, `v1.0.0-beta.13`'s installer with `--updated /S` — the updater's arguments — over `v1.0.0-beta.10`, with the installed entry, the folder and the uninstaller read, and the app not run. What was seen of the folder: a local build run over `v1.0.0-beta.10` stayed in its folder (#79), and so did that second try — an install of `v1.0.0-beta.10` or `.11` stays in `Programs\@sciadesktop` through every later installer, until it is uninstalled. **The Linux packages have never been built** (`docs/development/release-flow.md`, "Not there yet").
- Engine: downloads over several connections with dynamic segmentation, pause and resume, a queue, retries after an interruption, safe names that never overwrite, state saved on disk.
- Electron app: a window with its own title bar, supervision of the engine, orderly quit, resume after a restart.
- Interface: adding by paste, a list with the segment bar, filters, basic settings.
- Extension (Chromium): "Download with Scia" menu, media detected in the page, optional hand-over of the browser's downloads. **Written and covered by tests in its logic; not yet tried in a real browser.**

## M1 — Daily use

**The first stable release waits for the whole of this milestone and for AllDebrid (#7) — whole, and tried by the owner with their own key** (the owner, 19 November 2026; a link sent by the extension is not part of it — the owner, 20 November 2026, on #7: it goes through the same step, and is tried with the extension in a browser, M2), and ships for Windows only: Linux comes after it, below. The repository is public (the owner, 20 November 2026, #28), ahead of it, so that automatic updates are proven on a beta with installers first. The order, decided the same day: the mark on downloaded files and the second press before a program is run (#22); what the review of the tray left that needs no hands (#13); then choosing the folder, the speed limit, the notification when a download ends and automatic updates — alternating, in small PRs, with AllDebrid (M3, #7), so that neither waits for the other to be whole; the rest of the milestone follows in the same alternation.

## M2 — The whole extension

- Tried in Chrome and Brave first — the owner's choice (#23) — then Edge; a version for Firefox.
- Published in the stores. Each store's policy on downloading media from streaming sites has to be read, not remembered — and before pages, playlists and channels are built, not at the moment of submitting: the media the extension detects, the adaptive streams and #8 all stand on what it says.
- Downloads behind a login: sending the session's cookies, an explicit choice per site. The session comes from the extension only — never a cookie pasted by hand, never a default (the owner, 19 November 2026). The ADR on handing cookies over, which ADR 0002 announces, is still to write and has to record it. yt-dlp can read a browser's cookie store by itself: Scia never asks that of it ([ADR 0009](../adr/0009-the-video-of-a-page.md), point 3), and a spec holds it.
- **The video of one page** (#89), before the rest of this milestone and needing nothing of it: a pasted link that is a page of a site yt-dlp knows downloads the video the page plays, at the best quality Scia can fetch, instead of the page — public videos only, no session ([ADR 0009](../adr/0009-the-video-of-a-page.md); the owner, 20 November 2026). In four pieces: (1) a video offered as one file, with yt-dlp shipped — **written, covered by specs, and seen in the real app on Windows** with a video of archive.org, beside a local page saved as it stands (#97, #101); a page of a known site that plays no video is saved as it stands too (decided on #89 while the owner was away, the owner's to reverse); not seen: any other site, a pause in the middle of a read and the refusals on a row by hand, the installed app, Linux; (2) a video offered as an HLS stream, downloaded by the engine piece by piece and made into an mp4 inside Scia, in JavaScript, with no ffmpeg (the owner, 20 November 2026, on #98; [ADR 0010](../adr/0010-a-stream-made-into-an-mp4-inside-scia.md)) — **written and covered by specs against local streams; not seen on a site**: that check is the owner's; AES-128 with a public key included, DRM excluded; a stream that changes partway refused for now (#123); not seen: any stream in the app — its row was seen only from a staged state in review; a live stream recorded until stopped is #121, not built; (3) picture and sound offered apart, joined into one mp4 inside Scia — not built; (4) the shipped yt-dlp brought up to date by Scia at most once a day, against its published checksums — not built. Whether the first stable release waits for it is not decided. Later, a reader of sites of Scia's own beside yt-dlp, with a switch between the two, is the owner's wish (#102): not designed yet.
- Adaptive streams (HLS, DASH): detection, choice of quality, assembly. DRM is refused; HLS with AES-128 whose key the page's player gets is downloaded (the owner, on #98). The HLS of a page's video is piece 2 of #89.
- **Pages, playlists and channels** (#8): the address of a page, a playlist, a channel or a profile is expanded into the videos it lists, following its pages to the end; the list is shown to confirm, then downloaded. A private playlist, or anything else behind the person's own login, is read with the session of their own browser, on the explicit per-site choice above. The owner answered the question this item carried (19 November 2026): yes, as JDownloader does, inside the "Respect the hosts" principle as `CLAUDE.md` states it. Decided with it: sites are read by yt-dlp (thousands of sites, kept up to date by its community), shipped with Scia and updated by it, not by a reader per site written here ([ADR 0009](../adr/0009-the-video-of-a-page.md), which answers the objection ADR 0001 made to aria2). yt-dlp can do more than the principle allows — it can work around geographic restrictions: Scia never asks it to, and a spec holds that. It depends on the adaptive streams and on the session hand-over of this milestone.
- A fallback port, and the extension finding the app by itself, when 47821 is taken.

## M3 — Integrations: debrid services

M3 does not wait for M2: a hoster link pasted into Scia needs nothing from it. Only the link sent by the extension leans on an extension that has not been tried in a browser yet.

Integrations arrive one at a time. Each is visible in three places: an **Integrations** section in Settings that lists the services and shows which are connected; the Integrations table in the README; the release notes of the version that brings it (`feat(integrations): …`).

The first stable release waits for every line below but magnets and a second service: those lines are what #7 lists under "Done when", which has more that has no line here. It does not wait for the link sent by the extension, which the AllDebrid line names (M1, above).

- **AllDebrid** (#7), connected once in Settings (API key kept by the operating system). From then on **a hoster link pasted into Scia, or sent by the extension, is recognised, unlocked and downloaded automatically**, with nothing else to do — as a direct link would be. It has to be built and proven against a simulated service; the verification with a real account is the owner's, who pastes their own key into Settings. The first stable release waits for it, whole and tried by the owner (M1, above). It is built in small PRs, each with its issue. **The connection in Settings (#47): written, covered by specs, and seen in the real app on Windows against a simulated service** — a key the service does not know refused in words by its field, which kept what was typed; the right key connected, with the account's name and the day its premium ends; the key on disk sealed by the system, and nowhere in the log or in the page; still connected after the app was closed and opened again, and after the engine alone was killed and started again — but not after the whole app was killed within seconds of connecting (#69); disconnected at the second press, with its file gone; a service that does not answer said so. By keys alone as well: the refused key, the connection, the disconnection at the second press, the service that does not answer. Looked at in every theme of #52 and both variants, on the head of #54 that merged this in: the connected service, and the field with a refusal — the light variants with the page told to be light, against the simulated service; the second press that disconnects in Ice, in that PR's review ([ADR 0004](../adr/0004-the-key-of-a-service.md)). Nothing draws the key's field at rest but its line, under what WCAG asks (#66). Not seen: a real account with a real key, which is the owner's to try (#7); a hand on the keys (a script pressed them); a connected service whose key AllDebrid no longer accepts, blocks, or whose account it bans, a connected service while AllDebrid is slow or does not answer, and a system with nothing to seal a key with (each held by specs, never met in the app); Linux; the packaged app. **The unlocking of a pasted link (#48): written, covered by specs, and seen in the real app on Windows against a simulated service** — a link of a host the account takes unlocked and downloaded over several connections, byte for byte; a link the service needs time to prepare waited for (15 s, three questions at five seconds), then downloaded; a direct link pasted beside them fetched as it stands, and never told to the service; two links the service refused, each saying why on its row; a download of 96 MB through the service with the app killed at 30 %, taken up again from its bytes after a restart with the link the service had given, the service asked once for it; the direct link the service gave in `state.json` only, not in the log and not in the page ([ADR 0005](../adr/0005-a-service-resolves-a-link.md)). **Tried once with a real account** (20 November 2026, a disposable key of the owner's kept in an environment variable, one Rapidgator link of 2.5 GB, the app driven by a script): the link was recognised and unlocked by AllDebrid, and downloaded over several connections at up to 141 MB/s as its row showed it — and none of three runs finished: the direct link AllDebrid gave answered parts of the file with **204 No Content**, and once answered the first byte with a 200 that carried only that byte, read as a file of 1 B. Minutes later the same link answered everything as a host should, 32 ranges at once included. Scia now retries a 204 as a busy answer, asks the length again when a 200 carries only the byte asked, and says on a failed row that the link the service gave no longer works and that "Retry" asks for a new one ([ADR 0005](../adr/0005-a-service-resolves-a-link.md), point 12) — **held by specs, and seen in the real app against a simulated host that answers as the real one did; not yet tried against the real service.** In the third run the key was in no file of the profile, and disconnecting removed it. **Also seen in the real app against a simulated service:** a blocked key said on its row, whole, on two lines at the window's own size (`docs/design/a-failure-in-full.png`); the last list of hosts kept between runs, gone by after a restart while the service did not answer, and gone at a disconnection. Not seen: a download through the real service that finishes (the owner's, #7); any refusal of the real service on a row; a link the real service has to prepare; a direct link that has expired when a download is resumed; a service that cannot say which links are its own while a link is added, a link the service prepares that then fails, the 30-minute limit on a link being prepared, and these refusals on a row — a key no longer accepted, an account that is not premium, a host that is unavailable, a link with a password, a link the service could not unlock, AllDebrid not answering for a link, an account it bans, a network it does not serve, a link whose service was disconnected since it was added (each held by specs, never met in the app); a link pasted by a hand (a script typed it); Linux; the packaged app. The owner answered the question this item carried (19 November 2026): a debrid service is lawful under "Respect the hosts", and a hoster's wait or daily cap is not an access control Scia evades — the person pays the service, the service fetches the file with accounts of its own, and Scia downloads the link it is given. The principle says so (`CLAUDE.md`, #46).
- A download that went through a service says so in its row (#48): "via AllDebrid", last on its line, while it runs, paused and finished; seen in the real app while it runs and finished, with the rest of #48 — paused, held by specs only.
- A link that expires during a long download is unlocked again without losing the bytes. A PR of its own, after #48.
- A link that unlocks into several files shows the list before downloading. A PR of its own, after #48.
- A hoster link without a connected service says so, and says what to do (#49): with no service connected, Scia asks AllDebrid for the public list of its file hosts — no key, nothing of the link — and a link on one of those domains, or its `www.`, says "This link is on a file host: Scia downloads links like this through AllDebrid. Connect AllDebrid in Settings, then try again." instead of saving the host's page as the file (the owner, 20 November 2026; [ADR 0006](../adr/0006-a-file-host-without-a-service.md)). **Written, covered by specs, and seen in the real app on Windows against a simulated service** — with no service connected, a file host's link said so on its row and nothing was written to the folder; a direct link pasted beside it downloaded as before; the one request the service received was the public list, with no key; once connected, "Retry" unlocked the link and the file arrived byte for byte, compared with what its host sent (`docs/design/needs-a-service.png`). AllDebrid's real public list was read by a plain request outside the app, not by the app. Not seen: the real list in the app; a list that cannot be read while a link is added, one read again after six hours, a service that never answers, and a key connected while the list is read (specs only); Settings, Connect and Retry by keys (pressed with the pointer); a hand on the keys; Linux; the packaged app.
