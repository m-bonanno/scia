# Testing

| Layer       | Command                    | What it proves                                                                                                                                                                                                                                                                                                          |
| ----------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit        | `npm run test:unit`        | Rules: the domain, desktop engines, extension logic, React components                                                                                                                                                                                                                                                   |
| Integration | `npm run test:integration` | The downloader against a real HTTP host and a real folder; main's ear on the engine against a real HTTP host; the installer's include, compiled by electron-builder's makensis and run (Windows; makensis is fetched into electron-builder's cache the first time); the repository's scripts against the tools they run |
| Feature     | `npm run test:feature`     | The engine's API: tokens, scopes, status codes                                                                                                                                                                                                                                                                          |
| All         | `npm test`                 | The three above                                                                                                                                                                                                                                                                                                         |
| E2E         | `npm run test:e2e`         | The built app, started by Electron: what a person does, against hosts on this computer (`npm run build` first)                                                                                                                                                                                                          |

**The E2E suite and the smoke test start Electron, and run in CI only** (#171, #218): the owner works on this machine, and the app's windows take the screen. `npm run test:e2e` and `test:smoke` refuse to start outside CI unless `SCIA_E2E_LOCAL=1` is set by hand, and a bare `vitest run` does not list either project (they exist only when `SCIA_E2E=1`, which those two scripts set). An agent never sets `SCIA_E2E_LOCAL`.

## The gates' line

`npm run gates` ends with one line that says what the run was. CI's `Format, lint, types, tests, build` job runs the same script: the line ends the log of its `Gates` step, where a session reads it (`gh run view --job <id> --log`), and is written to the summary of its run, which GitHub shows only to someone signed in and gives through no API; a PR body links CI's runs of its branch instead of carrying a line, so a new head leaves the body as it is (the owner, 26 November 2026, #373, in place of the line pasted in the body of #342). A line made on this machine is read where it is reported: the tech lead's review of a first round carries its own.

- **What it says**: the head the run began on (`git rev-parse --short HEAD`), the workers (`SCIA_TEST_WORKERS=<n>`, or the words "Vitest's own count of workers" when it is not set to a positive whole number), the time of the whole run, and the test gate's counts in the words of Vitest's summary — `Test Files` and `Tests`, each failed, passed, skipped and todo where there are any, of the total. On a PR, CI tests the head merged into its base, a commit GitHub makes: the line names the head, given by the workflow (`SCIA_GATES_HEAD`), and that merge.
- **Where the counts come from**: Vitest's JSON report, which the test gate writes to `node_modules/.cache/scia-gates/vitest.json` beside its dots, and which the script deletes before each run, so that no earlier run's report gives a line its counts. The report calls a file only passed or failed; a file none of whose tests runs is counted skipped, as Vitest's summary counts it (`scripts/gates.mjs`).
- **A red run**: a red test gate gives the same counts, failed ones first, and the failing files by name — or, when it is red with no test failed, for an unhandled error, which the report does not name, the words "no test failed: Vitest's errors are printed above"; a gate red before the tests gives none.
- **A tree with changes not committed** is not the head: the line says so beside the head. An untracked file counts, since Prettier, ESLint and Vitest all read it. The run before a PR is opened, and the tech lead's, are made on the head alone: files of other work moved out of the tree first, or the run made in a worktree of its own.

## Where CI runs them

The pipeline is [ADR 0008](../adr/0008-the-delivery-pipeline.md). The gates are one workflow, `.github/workflows/gates.yml`: run on every PR; called by `release.yml`, on the commit a merge into `develop` or `main` makes, before it is tagged — the smoke test left out, as the release smokes its own installer; and called by `burn-in.yml`, several times on one commit ("Burn-in", below):

| Job                                 | Runner           | Runs                                                                                                           |
| ----------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `Format, lint, types, tests, build` | `ubuntu-latest`  | ADR numbers, format, lint, types, the three layers above, the build                                            |
| `Windows tests, build`              | `windows-latest` | the three layers above, the build                                                                              |
| `E2E (Windows)`                     | `windows-latest` | the build, then the E2E suite; the captures its specs take, uploaded as the artifact `captures` on a PR (#143) |
| `Installer smoke (Windows)`         | `windows-latest` | the installer of the commit, then the smoke test                                                               |
| `Quarantine (report only)`          | both, PRs only   | the specs in quarantine; not a gate (ADR 0019)                                                                 |

A spec that holds on one system and not on the other is a bug of the spec or of the app on that system: Windows rounds a timer under 16 ms up to 16, and forgives a path written with the wrong separator, which Linux does not.

**No retries.** A spec that fails in CI without a cause in the change is not run again until it passes. It is filed as an issue with its log (or the log is added to its issue), then fixed, or put in quarantine until it is ([ADR 0019](../adr/0019-specs-in-quarantine.md), #186). On a PR that does not touch it, the run is started again once, so that the PR's own checks are read; that is not a review round (`review-flow.md`, "What is blocking").

- **Quarantine** is `[flaky #N]` at the end of the spec's name, `N` its issue, in the `unit`, `integration` and `feature` projects. The gates and `npm test` pass it over (`testNamePattern` in `vitest.config.ts`); `npm run test:quarantine` runs those specs alone; CI runs them on every PR in "Quarantine (report only)", on both systems — not a required check, never a gate.
- The renderer's specs and the E2E suite have no quarantine: a flaky one is fixed, or skipped with its issue's number beside it.
- A spec leaves the quarantine only with its fix, in the PR that closes its issue, after `npm run test:quarantine` and the job are read green.
- The roadmap does not count a quarantined spec as holding what it tests.

### Burn-in

A new job of the gates becomes a required check of `develop` and `main` only once it has run ten times in a row green on CI (the owner's decision 4, [ADR 0008](../adr/0008-the-delivery-pipeline.md)). The **Burn-in** workflow (`.github/workflows/burn-in.yml`) runs them: **Actions → Burn-in → Run workflow**, or `gh workflow run burn-in.yml --ref develop -f runs=10`, on `develop`'s head.

- It runs the whole of `gates.yml` — every job, the installer's smoke test included — `runs` times side by side, at most four at a time — sixteen jobs of the twenty a free account runs at once, so that a PR still finds room — each run in its own concurrency group; one that fails stops none of the others.
- **Ten green runs of one commit are a burn-in.** A run that fails is a failed burn-in: its log goes into an issue, the job is mended, and the burn-in starts again from zero on the mended commit — never a run again until ten pass.
- A burn-in uses free runners shared with every PR: it is started when nothing waits on them, and not again for a job already burned in, unless that job changed how it runs.
- A run of Burn-in that shows an E2E spec's holds failing is not a burn-in: "A hold seen failing in CI", below.

## Writing a spec

- The name of a spec is the rule it holds: `'never overwrites a file already in the folder'`.
- One behaviour per spec; arrange, act, assert, with a blank line between.
- Integration specs compare **bytes** (`Buffer.compare`), not counters that could agree by accident.
- No fixed sleeps. Wait for a state with `until(() => …)` (`apps/server/src/testing/scratch.ts`); inject delays (`retryDelayMs`). A wait that is the case itself is not a wait for an outcome — a reader that stays away from a host, the stretch over which a rate is measured — and says so where it stands, in the disable comment of the lint rule that holds this one: `// eslint-disable-next-line scia/no-fixed-sleep -- the case itself: <why>` (`scripts/lint/no-fixed-sleep.mjs`).
- An integration spec has 15 s before Vitest gives it up (`vitest.config.ts`), not the default 5: real hosts, processes and disks wait on a machine shared by several sessions. What a spec asserts of time it bounds itself (`expect(took).toBeLessThan(…)`), never through Vitest's limit.
- Each spec gets its own temp folder and its own host (`startRangeServer`), and removes them. A temp folder is made whole by `mkdtemp`: lint refuses `join(tmpdir(), '<literal>')`, a name anyone can make first.
- A host that misbehaves is an option of `startRangeServer` (`drops`, `ranges: false`, `status`, `announcesLength: false`), not a mock of `http`.
- A service Scia connects to is a local host as well: `startAllDebridServer` (`apps/server/src/testing/alldebrid-server.ts`) answers as AllDebrid's documentation says, and refuses or misbehaves when told to. Every key in a spec is made up; no spec and no run uses a real one.
- Never hardcode a Windows path separator in a spec: build paths with `path.join`. CI runs every spec on Linux and on Windows. Lint refuses a `\` beside a template's `${…}` or a `+`, or given to `join` and `split`; a Windows path that is a value, such as a setting's folder, is left alone.

## E2E

`apps/desktop/e2e/`, run by Vitest as the project `e2e` with `playwright-core`'s Electron driver ([ADR 0008](../adr/0008-the-delivery-pipeline.md)). It starts the app `npm run build` made, as `npm start` does — not the packaged exe, whose installer is the smoke test's (below).

- **One app at a time** (`fileParallelism: false`), each started by `launchScia` (`e2e/scia.ts`) with a profile of its own (`scratchProfile`: its log, its engine's state, its downloads) and `--port=0`, the engine taking a free port: a spec never meets another, another session's run, or the installed Scia. `launchScia` sets the port and the profile itself, and refuses a spec's own.
- **What a spec starts ends after it, whatever happened** (`useRun`): its apps — closed, and killed when they do not end, also when their start failed — its hosts and services, its profiles; and the log of main is printed for a spec that failed, as a CI runner keeps nothing else.
- **Hosts and services are local**, the ones the other layers use: `startRangeServer` and `startAllDebridServer`, imported from `@scia/server/testing/*`, and `until` from `@scia/server/testing/scratch.ts`. **No spec reaches a host that is not on this computer**: with no service connected, Scia still asks AllDebrid which hosts are its own (ADR 0006), so `launchScia` points every app at a simulated AllDebrid that knows no account, unless the spec names its own; and an app whose yt-dlp was fetched asks for yt-dlp's latest release (ADR 0011), so `launchScia` points it at a host of releases (`startReleasesServer`, `--yt-dlp-releases=`) whose latest is the release Scia ships, unless the spec names its own; and a spec that pastes a Bunkr album points the app at a host that answers as Bunkr does (`startBunkrServer`, `--bunkr=`), never Bunkr. Every key is made up.
- **The yt-dlp Scia ships is there**: CI's E2E job fetches it after the build (`node apps/desktop/scripts/fetch-tools.ts`, as `npm start` does), and the spec of its update fails, naming that command, when it is missing.
- **A person's road**: links are pasted in the bar and its button pressed (`paste`), Settings is opened and its controls used, the window is closed with `BrowserWindow.close()` from main — Electron's documented equivalent of its X: a close the window prevents and hands to main, the same road as the system's close message of "Proving the real app", item 5. The one thing answered for the person is the system's folder dialog, which a script cannot press (`dialog.showOpenDialog` replaced in main).
- **The window takes the spec's pointer, not the system's**: `launchScia` sets `setIgnoreMouseEvents(true)` on it, so the real cursor crossing it — a hand, another session's window — sends the page no pointer event, while playwright-core's own still reach it. A hover held for seconds (a notice under the pointer) failed 3 runs in 12 without it.
- **The variant, light or dark, is the system's, in the page as in main**: playwright-core tells the page that the system asks for light unless it is launched with `colorScheme: null`, which `launchScia` passes — without it main painted the window's buttons dark over a light page on a dark Windows (#155). A spec that needs a variant sets it as the system would, in main (`nativeTheme.themeSource`), and the page and main follow it together (`e2e/window.e2e.test.ts`).
- **An answer the engine cannot be made to give is given in its place, on the page's road only** (`page.route`): the notices' spec answers four adds with four refusals, the fourth once the focus is placed. It is the one stand-in for the engine; what the engine itself does is proven against the engine.
- **What a row does not say is read from the engine**, as the page reads it (`downloadsOf`): the bytes that arrived, the status of every download. `allCompleted` is false for an empty list.
- **Every wait is for a state** (`until`, on `performance.now()`), with bounds set for a cold start on a CI runner. A bound on a time is set against what the app does without the thing held, and counted from where the thing begins — the speed limit's spec is owed eight seconds from the host's first range, waits for more than six, and the file arrives in milliseconds without the limit, also when AllDebrid's public list never answers; at twice the limit it would take four.
- Each spec was seen failing with the line it holds taken away; a new one is too (`.claude/gotchas.md`, "Specs"), in CI: "A hold seen failing in CI", below.

Run locally, its windows open on the screen, and a first close into the tray shows the system's notification, every profile being new. What it does not reach, and stays with a person or with a harness: the system's notifications and the tray as they are drawn, a hand on the mouse or the keys, a page's `visibilityState` — playwright-core keeps the page `visible` when the window is minimised or hidden; a harness that starts Electron itself and reads the page over DevTools sees it (#138) — the packaged app (the installer's smoke test, below), Linux.

### A hold seen failing in CI

The E2E suite runs in CI alone, so an E2E spec's holds are seen failing there, on a branch that lives until the last of its runs is read (#312, #317):

1. **A branch from the head under review**, named `test/<issue>-holds-seen-failing`, `<issue>` the number in the name of the PR's own branch: the branch is that issue's work, as [`git-flow.md`](./git-flow.md) asks of every branch, and no issue is opened for it. #312's carried the PR's number instead (`test/312-holds-seen-failing`).
2. **A commit on it**: the spec as the head under review has it, and a variant of it for each hold — a copy of the spec beside it in `apps/desktop/e2e/`, under a name of its own that ends in `.e2e.test.ts` (the `e2e` project collects no other file), with the one line the hold answers put back as it was before, and nothing else changed. A line of the app, or of the E2E tooling every spec shares, cannot be put back for one variant alone: each such line gets a commit of its own on the same branch, made once the run before it is read, the variants taken out — a commit that changes that one line from the head under review, and nothing else.
3. **A run of each commit, by Burn-in**, which runs the gates on the branch it is given, with no PR and nothing released: `gh workflow run burn-in.yml --ref test/<issue>-holds-seen-failing -f runs=1`, once for each commit, started when nothing waits on the runners, as a burn-in is.
4. **Each run's log read**, `E2E (Windows)`'s. In the variants' run, the spec passes and each variant fails at its own hold and nowhere else; in the run of a line of the app or of the shared tooling, the spec fails at the hold that line answers and nowhere else. Each failure with the numbers its hold printed, and no "Unhandled Rejection". The PR body gives each run's number and each failure, with its numbers.
5. **The branch deleted** once the last run's log is read (`git push origin --delete test/<issue>-holds-seen-failing`). It is never merged, and no PR is opened from it.

- **When**: for the holds of an E2E spec, on a PR of the team. The other layers run on this computer, and their holds are seen failing here. A variant, or a line of the app, whose run fails beside its hold, or not at it, proves nothing of it: it is mended, and the run made again on the mended commit. The spec itself failing in the variants' run is a failure of the spec, handled as "No retries" says (above).
- **Not a burn-in**: the workflow only carries the runs. They are meant to be red, count toward no job's ten green runs, and their failures are the evidence the PR body gives, not a failed burn-in: no issue is filed for them.
- **A network guard**: none is needed when nothing put back on the branch can reach past the runner — every line put back is one CI has already run, on an earlier head of the PR or on `develop`, and none touches where a run points: an address, a host `launchScia` names, a link fetched as it stands. Unlike a mutation run on this computer (`.claude/gotchas.md`, "Specs"), a run of Burn-in has no guard loaded into its processes, so a line that would need one is not put back this way: such a line is held by a spec of another layer too, one that asks nothing of the network (the address a `site` gives, read back), and that spec is seen failing on this computer, behind the guard.

## The installer's smoke test

`apps/desktop/e2e/installer.smoke.test.ts`, the Vitest project `smoke` (`npm run test:smoke`). One road, in order: it installs the NSIS installer named by `SCIA_INSTALLER` silently (`/S`); checks `Scia.exe` and its uninstaller are in `%LOCALAPPDATA%\Programs\scia`, and its version in the uninstaller's registry key; writes a newer version into that key and runs the installer again silently, which must end with 1638 and leave the folder and the keys as they were ([ADR 0018](../adr/0018-the-installer-refuses-an-older-version.md)), then puts the version back and installs the same version again, as a repair; checks that the yt-dlp the packing fetched, in its `resources\tools`, answers `--version` with the version `apps/desktop/src/engine/runtime-layout.ts` fixes; starts the installed exe as it ships (`launchInstalled`, below) on a scratch profile and a free port, against a simulated AllDebrid and a local host of yt-dlp's releases, and reads on its stderr that `--inspect`, asked for, opened no debugger (#115); reads in its log that it is the packaged app of `SCIA_VERSION`, that its engine is ready and that nothing is an error, main's or the engine's; downloads a pasted link from a local host, byte for byte; runs the installer again, silently, during a slow download, and reads that Scia was told its session ends and ended with its state written before the installer did, then starts it again and sees the download finish (#13); quits by closing its window; and uninstalls silently until its folder is gone.

- **The installed exe is driven without main** (`apps/desktop/e2e/installed.ts`, #115). Its fuse `enableNodeCliInspectArguments` is off, and playwright-core's Electron driver reaches main through `--inspect`: the spec starts the exe itself with Chromium's `--remote-debugging-port=0`, reads the port's address on its stderr, drives the page over it (`connectOverCDP`) and closes the window by the system's `WM_CLOSE`, as its X closes it. The exe tested is the exe shipped.
- **It runs on a Windows CI runner only.** An install replaces the Scia installed on the machine: the spec refuses to start without `CI=true`, Windows, `SCIA_INSTALLER` and `SCIA_VERSION`. On a person's computer the packaged app is tried unpacked, which installs nothing: `npx electron-builder --config electron-builder.yml --dir --publish never` in `apps/desktop`, then `launchInstalled(profile, 'release/win-unpacked/Scia.exe')`.
- **Where it runs** ([ADR 0008](../adr/0008-the-delivery-pipeline.md)): on every PR and in a burn-in, on an installer packaged from the commit at version `0.0.0` (`gates.yml`, `Installer smoke (Windows)`); in every release, on the installer with the release's version, **before its files are attached** (`release.yml`): a failure attaches nothing.
- **A release's smoke test reaches GitHub.** At a release's version the updater is on (ADR 0007) and reads this repository's releases; at `0.0.0`, on a PR, it is off and nothing leaves the runner. The spec refuses a run in which an update was installed at the quit: what was tried is what is uninstalled.
- **What it does not reach**: an install over an earlier Scia, and the update from one release to the next; SmartScreen on a downloaded installer; a person's hand. Those stay with a person ([`release-flow.md`](./release-flow.md), "Releasing").

## Proving the real app

What the E2E suite can hold is held there. What it cannot — something the system draws, a timing it cannot set up, a run longer than a CI job — is proven by hand, and the PR body says what ran:

1. `npm start` — builds everything and launches Electron with `--user-data-dir=.dev-profile --port=47822`.
2. Do the thing; then read `apps/desktop/.dev-profile/logs/main.log`. A healthy-looking window has hidden a dead subsystem before: **read the log**.
3. For a download, point it at a local host rather than someone's server. For a service, start the simulated one on a port and launch with `--alldebrid-api=http://127.0.0.1:<port>`: the engine takes an address on this computer and no other. A run whose yt-dlp was fetched (`npm start` fetches it) asks GitHub for yt-dlp's latest release once a day (ADR 0011) unless it is launched with `--yt-dlp-releases=http://127.0.0.1:<port>`, a host that answers as `apps/server/src/testing/yt-dlp-releases-server.ts` does. A Bunkr album pasted in such a run reads Bunkr itself unless the run is launched with `--bunkr=http://127.0.0.1:<port>`, a host that answers as `apps/server/src/testing/bunkr-server.ts` does. The key typed in such a run is one the simulated service was given, never a real one.
4. To drive the window from a script, add `--remote-debugging-port=<n>` and speak the DevTools protocol to it. Such harnesses are not committed.
5. To close the window as its X does, send it the system's close message (`(Get-Process -Id <pid>).CloseMainWindow()` on Windows): the page's own `window.close()` and the protocol's `Browser.close` are different roads, and neither is the person's.
