# Git flow

`main` ← `develop` ← `<type>/<issue>-<kebab-description>`.

- `main` is what was released. `develop` is the default branch, where work lands.
- A branch is cut from `develop` for one issue: `feat/12-tray-icon`, `fix/31-resume-after-sleep`. Types are those of `commitlint.config.js`. Related fixes filed together may share one branch, named after one of them, whose PR closes all their issues (the owner, 21 November 2026, #168). A branch that only shows an E2E spec's holds failing in CI is cut from the head under review instead, takes the issue number of the PR's own branch (`test/<issue>-holds-seen-failing`), is never merged or opened as a PR, and is deleted once the last of its runs is read ([`testing.md`](./testing.md), "A hold seen failing in CI").
- **Nobody commits or pushes to `main` or `develop`.** `.husky/pre-commit` and `.husky/pre-push` refuse it (`protected-branch-guard.sh`). Automation that legitimately must sets `HUSKY=0`.
- **A Claude session is guarded before each shell command** (the owner, 26 November 2026, #382). `.claude/settings.json` runs `scripts/claude-guard.mjs`. It refuses what these runbooks forbid: a write to `main` or `develop`, skipping the git hooks, a tag or a release by hand, a merge of a head not approved, an inline or attributed body, an unassigned issue or PR. It asks the owner for what is theirs to do: a merge commit, closing a PR, the repository's settings. Its rules, each with its reason, are listed in the script, the one place they are written. It is code that runs on every command, so a PR from outside that changes it is opened in no session ([`review-flow.md`](./review-flow.md), "A pull request from outside").
- Commits follow Conventional Commits with a lower-case subject; `.husky/commit-msg` runs commitlint.
- When `develop` moves ahead, merge it into the branch. No rebase of pushed work, no force-push. After every merge of `develop`, run `npm run check:merge` (the owner, 26 November 2026, #374): on `changed`, do the read its line names — what the merge brought into the files whose own diff it changed — for a line left twice or put back, before pushing. `docs/product/decisions.md` merges with git's `union` driver (`.gitattributes`): both sides of a conflict are kept, so a line one side edited in place beside the other side's change is left twice, old and new. `.claude/gotchas.md` has no driver — its entries are edited in place too often — and conflicts as before; #378, which splits it by area, is to cut those conflicts. What a merge does to the team's verdict: [`review-flow.md`](./review-flow.md), "Rules".
- A work branch is **squash-merged** into `develop`, the PR title becoming the commit. `develop` → `main` is a **merge commit**, so `main` keeps every change that went into a release, and so is `main` back into `develop` after it. Who merges what, and when: [`review-flow.md`](./review-flow.md).

## A pull request

1. Title: `type(scope): description`, lower-case — `type(scope)!: description` for a breaking change ([`release-flow.md`](./release-flow.md)).
2. Body from `.github/PULL_REQUEST_TEMPLATE.md`, in English, written to `.claude/pr-bodies/<branch>.md`.
3. `Closes #N` in the body, naming the issue the PR is for — each of them, on a branch that related fixes share: the `Linked issue` check fails a PR whose body closes no issue of this repository (`scripts/linked-issue.mjs`).
4. Before opening it, run the gates locally: the list is in [`review-flow.md`](./review-flow.md#the-gates).
5. **Opened with `npm run pr:open -- "<title>"`** (`scripts/open-pr.mjs`; the owner, 26 November 2026, #373). It refuses a title commitlint refuses, opens the PR into `develop` with the body of point 2, assigns it to whoever opens it — the owner's account, for the team — and labels it (the owner, #225): the type label of its title, and an `area:*` label for each area its paths touch, as the script's lists say. A label no path tells, such as `area:integrations` or `accessibility`, is added with `--label <name>`. The two PRs of a release are opened by hand: "The two PRs that have no issue".
6. **A PR from outside the team** carries no label or assignee its author set: they have no right to set them here. The session that runs `/team-review` on it adds the labels the script's lists give, and assigns its author: `gh pr edit <N> --add-label <labels> --add-assignee <author>` — never `@me`, which would assign the owner (#227). An issue the team opens is labelled the same way from the start, `gh issue create … --label <type>,status:accepted` plus an `area:*` label for each area it touches, and assigned to whoever will build it (`--assignee @me` when that is the team).
7. The team reviews it. When it is merged, how, and on whose word depends on the kind of PR: the "Merging" table of [`review-flow.md`](./review-flow.md).
8. No AI attribution anywhere.

## What the type of a commit decides

The title of a PR becomes the commit on `develop`, and semantic-release reads it to choose the next version: which type releases what is the table of [`release-flow.md`](./release-flow.md), the one list. A `fix` hidden under `chore` never reaches anyone.

## Work in parallel: sessions, numbers and issues

Sessions work side by side, each on its own branch, and each sees only `develop` as it was when it began. How many, and how they share the machine, is the owner's choice of 24 November 2026 (#337), after a day of five sessions at once: a load average up to 210, four or five review rounds per PR, and a conflict in `docs/product/decisions.md` at nearly every merge.

- **At most two sessions at once**, and a second only for work that touches other files than the first's.
- **PRs on the same area one after another**, not side by side.
- **The local gates with `SCIA_TEST_WORKERS=2`, one run at a time** on the machine: `SCIA_TEST_WORKERS=2 npm run gates`, started once no other session's run is going (`pgrep -fl scripts/gates.mjs` lists none).
- **A session stops only its own processes**, by the id it started them under (`kill <pid>`), never with `pkill -f` on a pattern other sessions' processes share — `vitest`, `electron`, `node`.

- **An ADR takes the next number free on `origin/develop` and in every open PR**: `git fetch` and `ls docs/adr`, then `gh pr list --json number,files --jq '.[] | .number as $n | .files[].path | select(startswith("docs/adr/")) | "#\($n) \(.)"'`. Read it again before the merge: a PR merged meanwhile may have taken it. The gates refuse two records of one number (`npm run check:adr`, #183) — on a PR's head, which can be older than another PR's merge (`develop` does not ask a branch to be up to date), and again on the merged commit before it is released: #158 and #177 both took 0016, and git, seeing two file names, merged both.
- **A follow-up issue is searched for before it is opened**, open and closed: `gh issue list --state all --search "<its key words>"`. #151 and #176 were the same issue, opened by two sessions an hour apart. An issue the team opens carries its labels from the start: "A pull request", point 6.

## Repository settings

Set on GitHub: the repository is **public** (the owner, 20 November 2026, #28); default branch `develop`; squash merge and merge commit allowed, rebase merge off; head branches **not** deleted on merge.

- **Branch protection** of `main` and `develop` (the owner, #28): no deletion, no force-push, no push but the merge of a PR, and the PR's nine checks green — `Format, lint, types, tests, build`, `Conventional title`, `Linked issue`; since their burn-in (the owner, 20 November 2026, #93), `Windows tests, build`, `E2E (Windows)`, `Installer smoke (Windows)`; and since theirs (the owner, 25 November 2026, #332), CodeQL's `CodeQL`, `Analyze (actions)` and `Analyze (javascript-typescript)`. Admins are held to it too. A check's name is its job's name in `gates.yml` or `pr-title.yml`: a job renamed there is a check nobody reports, which blocks every PR until the branch protection of both branches, and this list, are changed with it. A new job of the gates is added here only after its burn-in ([`testing.md`](./testing.md), "Burn-in"). CodeQL's three checks are not jobs of `gates.yml`: they come from its default setup ("Code security", below), which names them. They run on every PR from a branch of this repository, a PR of docs alone included, and on none from a fork: GitHub's default setup leaves those out. So a PR from a fork, which the owner may ask for ([`review-flow.md`](./review-flow.md), "A pull request from outside"), is merged only once the owner has taken the three off `develop`'s protection by hand, and they are put back right after (the owner, 25 November 2026, #332). Their burn-in was read from their runs, since `burn-in.yml` runs `gates.yml` alone and cannot start the default setup: `Analyze (actions)` and `Analyze (javascript-typescript)` ran 59 times each, on pull requests and pushes, and `CodeQL` 46 times, on pull requests only — code scanning posts it on a pull request — all green, from 24 to 25 November 2026.
- **Approval by the owner** (a ruleset of that name on `main` and `develop`; the owner, 20 November 2026, #76): one approving review required, dropped by a new push. Only the owner has write access, so only the owner's approval counts. GitHub does not let the author of a PR approve it, so the repository's admin role may bypass the review — when merging a PR, never on a push: **a PR the owner's account opens** (every PR of the team) is merged with `gh pr merge --admin`, on what the "Merging" table of [`review-flow.md`](./review-flow.md) says; **a PR anyone else opens** (a fork, Dependabot) waits for the owner's approving review, given by the owner's own hand. Who merges, and on whose word: the "Merging" table of [`review-flow.md`](./review-flow.md). The husky hooks stay: they refuse a direct commit before GitHub does.
- **Why head branches are not deleted on merge**: the back-merge of a release is a PR whose head is `main`. The protection refuses to delete `main` now, and the setting stays off all the same, so that neither depends on the other alone. A work branch is deleted by whoever merges it, at the merge (`git push origin --delete <branch>`, or the button on the PR) — never with a flag on the back-merge.
- **Actions**: the workflows of a PR from a fork wait for the owner's approval, for every outside contributor; the `GITHUB_TOKEN` reads only, and no workflow may approve a PR. How such a PR is reviewed: [`review-flow.md`](./review-flow.md), "A pull request from outside".
- **Security, and what a stranger sees** (the owner, 24 November 2026, #310, #190): private vulnerability reporting on — the one channel of [`SECURITY.md`](../../SECURITY.md), of [`CODE_OF_CONDUCT.md`](../../CODE_OF_CONDUCT.md) and of the security link of the issue forms (`.github/ISSUE_TEMPLATE/config.yml`): turned off, all three lead nowhere; Dependabot alerts on, its security updates off. The topics (`alldebrid`, `debrid`, `download-manager`, `electron`, `hls`, `typescript`, `windows`, `yt-dlp`), the homepage set to the latest release, and the social preview, uploaded by hand from [`docs/design/social-preview.png`](../design/social-preview.png): GitHub has no API for it. No `good first issue` or `help wanted` label: the team opens every pull request (#221).
- **Code security** (the owner, 24 November 2026, #332; read back through the API the same day): CodeQL's default setup on — JavaScript/TypeScript and the GitHub Actions workflows, the default query suite, on every pull request and push and once a week; Secret Protection on — secret scanning's alerts, and push protection, which blocks a push carrying a supported secret. Off: Copilot Autofix, the AI Scan features and Agentic autofix, which consume AI credits (#314 holds the owner's decision on AI agents); secret scanning's non-provider patterns and validity checks, since generic patterns would flag the made-up keys of the specs — a fixture's key flagged is dismissed as "used in tests"; Dependabot security updates (alerts only, #190).
- **Labels**, beside each issue's and PR's type and `area:*` ("A pull request", points 5 and 6): `follow-up` — what a review left, collected in one issue ([`review-flow.md`](./review-flow.md), "Non-blocking findings are not lost"); `later` — after the first stable release; `needs-owner` — waits on a decision or a hand of the owner; `flaky` — a spec that fails now and then ([`testing.md`](./testing.md), "No retries"); `epic` — an umbrella issue for several PRs; `accessibility` — a barrier for people with disabilities.
- **Who can write**: the owner alone. An outside contributor works on a fork and cannot push, merge or label here ([`CONTRIBUTING.md`](../../CONTRIBUTING.md)).

## The two PRs that have no issue

A release (`develop` → `main`) and its back-merge (`main` → `develop`) close no issue and have no `<type>/<issue>-…` branch: their heads are `develop` and `main` themselves. The rule on branch names and `Closes #N` does not apply to them, nor `npm run pr:open`, which opens a work branch into `develop`. They are titled `release: vX.Y.Z` and `chore: merge main back into develop after vX.Y.Z`, and opened with their label and assignee: `gh pr create --base main --head develop --title "release: vX.Y.Z" --body-file .claude/pr-bodies/develop.md --assignee @me --label chore`, and the back-merge with `--base develop --head main`, its own title and `.claude/pr-bodies/main.md`. How each is merged, and by whom, is the "Merging" table of [`review-flow.md`](./review-flow.md).

The `Linked issue` check lets those two through, and the PRs Dependabot opens (`.github/dependabot.yml`), which no person writes and which carry no issue either; each is still reviewed as the "Merging" table says.
