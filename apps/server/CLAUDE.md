# Scia — Engine CLAUDE.md (`apps/server`)

Loaded when working under `apps/server/`. **Extends** the root `CLAUDE.md`; wins for the engine.

The engine downloads. It is a plain Node process: Electron forks it as a `utilityProcess`, the tests and `npm run dev` run it under Node. **It never imports `electron`** (ESLint enforces it).

## Rules

- **Ports where there is a seam.** `RemoteSource` (probe + open a range) is what HLS and any future source implement; `LinkResolver` is the step before it, which a debrid service plugs into; `StateStore` is what a database would replace. Do not add a port without a second implementation or a test that needs the seam.
- **The part file is the truth about bytes; `state.json` never claims more than the disk holds.** A checkpoint syncs the file first, then writes the state. A crash re-downloads a little; it never corrupts.
- **A ranged part file is made sparse, and its room is looked at, not reserved** ([ADR 0026](../../docs/adr/0026-a-part-file-made-sparse.md), #182). On NTFS a file whose size is set ahead of its bytes is filled with zeros up to a write far into it, while that write waits and holds one of Node's disk threads: 32 s with nothing written, for a 32 GiB file on an NVMe SSD.
  - Before its size is set — a new one while it is empty — the part file is made sparse (`sparseMarkerFor`): on Windows by the system's `fsutil sparse setflag`, by its full path under `SystemRoot`, with an environment built from nothing, ended after `SPARSE_LIMIT_MS`; elsewhere nothing is asked, a size set by `truncate` being a hole already. A refusal is logged (`part_file_not_sparse`, with the id) and the download goes on with the file dense: it never fails for it.
  - Before a part file is made — the first time, or again when the kept one is gone — the room left on its disk (`statfs`: `bavail × bsize`) is compared with the file's size. Less, and the download fails `DISK` before a byte is asked for, with no part file made. A disk that does not say its room is not checked. **A kept part file is not looked at again**: a dense one holds its whole size already, and counting what it has not written would refuse it room it has. The room is not reserved: what fills the disk afterwards is said by the write that finds it full, as before.
  - What the marker runs goes through a seam (`RunProgram`), so that a spec reads the file, its arguments, its environment (`{ SystemRoot }` and nothing else) and its limit, and a program that never answers is ended at the limit (`testing/never-answers.ts`).
  - The engine starts with `ENGINE_THREADPOOL_SIZE` threads for the disk (`UV_THREADPOOL_SIZE`, from `@scia/contracts`, given by main's `server-env.ts` and by `npm run dev`): one for each write its downloads can have at once, and four to spare, so that a save of `state.json` or a file of the page never waits behind a write.
- **A file is never overwritten.** Names are made unique against the folder and against the downloads still on their way there, and checked again when the part file is renamed. What a download keeps beside its name while it runs — `.scia`, `.scia.pieces`, `.scia.picture`, `.scia.sound` — is reserved with it: a name is taken when one of those is on disk or in the list, and when it is one of them for a download in the list.
- **A finished file carries its system's mark of what came from the network** ([ADR 0003](../../docs/adr/0003-the-mark-of-a-downloaded-file.md), `origin-mark.ts`): on Windows the `Zone.Identifier` stream, with the zone and never the address the file came from. It is written on the part file, before the name is looked at and the file renamed: the file never stands under its name unmarked, and nothing waits between "is the name free?" and the rename. A disk that refuses the stream gets its file all the same, and a `mark_refused` with its id in the log: a download does not fail for a mark.
- **Names from a host are hostile.** They pass through `sanitizeFileName` and lose any path before they touch the disk. A test covers every new source of names.
- **Retry what can heal, not what cannot**: a dropped connection, a 5xx, a 429 retry with backoff; a 404 or a 403 fail at once and say so. A 204 to a range is a busy answer too: a direct link of AllDebrid gave it for parts of a file it had not fetched yet, and the same ranges a moment later (#65). And a 200 to the first byte that carries only that byte is a range answered with the wrong status, not a file of one byte: the length is asked again without a range.
- **`Accept-Encoding: identity` always.** A compressed body does not match the ranges asked for.
- **One speed limit for everything** (`Throttle`, one in `DownloadManager`, over the `Pacer` of `@scia/core`). **A connection reads only against room booked before the read**: before it asks its host for a range it books one read's worth (64 KB, or what is left of its range when that is less) and waits its turn; before every read after that, when what it has booked no longer covers the largest read it has made, it books up to a whole read again. When it is done — finished, failed, paused, removed — it settles: what it booked and did not read is given back. A download that is paused or removed leaves nothing owed. A host is held back by not being read from; no byte that was read is thrown away.
  - **Nothing is read that the limit has not made room for, from the first byte, but for three things, each with its bound**:
    1. when a limit is set or lowered, each connection in the middle of a read finishes that read — one read at most — and pays for it before its next;
    2. a read larger than any its connection has made before passes what was booked by the difference — less than one read over the connection's whole life — and is paid for before the next;
    3. a booking may start up to 50 ms in the past, so that a wait that ends late is caught up: the limit is passed by no more than 50 ms' worth of it, and nothing beyond that is ever caught up. A system's timer may fire fifteen milliseconds late, which under a high limit is many reads' turns.
  - "Read" is what the engine takes from a connection. What the host has sent ahead of that — in the system's buffers and in Node's — is not counted: it is there once for each connection, it is not a rate, and it is how any limit that holds a host back by not reading works.
  - Under a limit the connections of a download open one after the other, as the limit makes room, and a connection's turn comes round every connections × 64 KB ÷ the limit: 40 s at the most Settings allows (160 connections, 256 KB/s). Over an encrypted connection a read is a record of 16 KB: one booking covers four.
  - **A connection held back is not a silent host.** `HttpSource` times a host's silence only while a read is waiting for it — never on the socket, which is quiet whenever Scia is not reading. That timer was also what ended an answer nobody read: a redirect's answer is closed, not drained, and what `open` answers is read at once (`remote-source.ts`).
  - It runs on a clock that never steps (`performance.now`), not the system's: a clock set back an hour would be an hour without a byte.
  - Changing or lifting it wakes whoever is waiting, to book again under the new limit; what was booked with the old one is forgotten. A download that is paused, removed or stopped does not wait on the limit: the wait ends with its signal.
  - **A limit is tried at both ends of the menu, against a host that does not pause, in bytes.** Three shapes of this were wrong, each invisible to the runs made of it: paid after the read, every connection's first read passed unpaid and stayed owed when its download was removed; booked only when nothing was left, the couple of hundred bytes an answer's headers leave of a booking let a whole read through, twice the limit while connections opened — hidden by a test host that paused between pieces; and with a wait before every read and none made up, a download under 25 MB/s got a third of it — hidden by runs that all sat between 256 KB/s and 2 MB/s.
- **`GET /events` is never silent for long** (`EVENTS_KEEP_ALIVE_MS` in `@scia/contracts`): with nothing to send, and between two lists, the stream writes a comment, which a reader of events passes over. Whoever listens can tell an engine with nothing to say from one that stopped talking, and a client that ends an answer after minutes without a byte — Node's `fetch`, after five — never meets one. The wait for a change is called off when the listener goes (`nextChange(since, gone)`): a stream that closed leaves nothing waiting in the manager.
- **`state.json` takes a new setting with a default** (`state-store.ts`): a file written before the setting existed loads, with the default — and so does one whose stored value the bounds of today refuse. A state that does not parse is set aside as `.unreadable` and the engine starts empty — so a setting added without a default, or a bound tightened later, would lose every download in the list. A save renamed onto a file another process holds open (on Windows: an antivirus, the indexer) is tried again for two seconds before it is given up and logged (`state_not_saved`, #151); the next change saves again.
- **The theme of the interface is a setting** (`theme`, one of `Theme` in `@scia/contracts/theme`; the page patches it), and **the page is served wearing it**: `data-theme` is written on the `<html>` of `index.html` at every request, so the page's first paint is in the theme, with no script and no answer to wait for. A state that names a theme this version does not have loads with the default one.
- **The download folder has a route of its own** (`PUT /settings/download-directory`, the app's token only): main names it after the person chose it in the system's dialog. It is not among the settings the page patches, so no type lets the page send a path. The engine takes an absolute path, keeps it as the system names it (`resolve`), makes the folder, and refuses one it cannot make or write to, leaving the settings as they were. **Writing is proven by writing** — a file of Scia's own made in the folder and removed — never by asking the system: on Windows `access(folder, W_OK)` says yes for every folder that exists. A download keeps the folder it was added with.
- **The key of a service is in the engine's memory and in the vault, and nowhere else** ([ADR 0004](../../docs/adr/0004-the-key-of-a-service.md)): never in `state.json`, in a log, in an error, in an address, or in an answer of the API — no route says a key back. `KeyVault` is the port: `ParentVault` asks main, which keeps the key sealed by the system; `MemoryVault` is what plain Node has, and keeps it as long as the process. A key is kept only after its service accepted it, and leaves the vault before it is forgotten: one that stayed would connect Scia again at its next start. A spec that says "never in the log" reads every line that was logged. `ParentVault` waits for a write `KEY_SEAL_LIMIT_MS` beyond its five seconds: main answers it once what opens the key is on disk ([ADR 0023](../../docs/adr/0023-a-key-said-kept-once-it-can-be-read-back.md)). **A key kept and not read back at a start is said** (`keyNotRead` in `GET /integrations`, until a key is connected again or the service disconnected), and meanwhile a link on the account's kept list of hosts — its domain or its `www.` — fails `SERVICE_NEEDED`, also when the public list cannot be read (#69).
- **The routes of a service are for the app's token alone**: `GET /integrations`, `PUT /integrations/:id` with `{ apiKey }`, `DELETE /integrations/:id`, and the three of a code (below). `400 INVALID_REQUEST` for what cannot be a key, before the service is asked; `422` with the service's refusal (`KEY_REFUSED`, `KEY_BLOCKED`, `ACCOUNT_BANNED`, `NETWORK_REFUSED` — AllDebrid's `NO_SERVER`, a server or a VPN it does not serve); `502 SERVICE_UNAVAILABLE` when it could not be asked; `500 KEY_NOT_KEPT` when the system will not keep the key; `404` for a service Scia does not know; `204` for a disconnection. Connecting and disconnecting happen one at a time, and a write that was given up on is undone: the vault is put back as it was. A listing waits two seconds at most for the service to say whose account it is, then answers what it knows.
- **A key also arrives by a code the person confirms on the service's site** ([ADR 0013](../../docs/adr/0013-a-key-that-arrives-by-a-code.md); `Integrations.startCode`, the owner's decision on #136). `POST /integrations/:id/code` asks AllDebrid for a code with no key (`GET /v4.1/pin/get`) and answers `201` with the code, its page, when it expires and its `status` (`502`/`422` as for a key, when the service gives none; `409 CONFLICT` while a service is connected, and for a code whose wait was ended while it was given); `GET` says what became of the code given last (`404` with none); `DELETE` ends the wait (`204`). The engine asks `POST /v4/pin/check` every five seconds, for the lifetime the service gives and ten minutes at most (`CODE_LIMIT_SECONDS`), on a timer that does not hold the engine open (`ref: false`, held by no spec); a service that cannot be asked for a moment is asked at the next turn; the code fails `CODE_EXPIRED` when its time runs out or the service no longer knows it (`PIN_EXPIRED`, `PIN_INVALID` — an answer to a code alone, never a download's failure: `CodeExpiredError`). The key a confirmed code gives is connected through the pasted key's own step, one at a time with the others; the `check` token never leaves the engine's memory. One code waits at a time: a new code, a pasted key (when it is sent and again once it is kept) and `DELETE` end the wait, and move it on a turn, so that a code the service gives after it is not kept; a `DELETE` that names a code (`?code=`) forgets that one only; a key a confirmed code gives that waits its turn behind another change is not connected once the wait has ended. A code's page is taken only on the service's own site (`isServiceSite` in `@scia/contracts`). Settings closing ends no wait (the owner, #146): **every snapshot says which services are connected** (`connectedServices`, from `Integrations.connected()`, the manager's `services`) **and the last confirmed code whose key connected nothing** (`codeConnectFailed`: the service, why — a refusal of the key or `KEY_NOT_KEPT`, never an expiry or a wait ended — and when), and `Integrations.onChange` wakes the events whenever a key is connected or let go and whenever such a code fails, so that main hears both with nobody in Settings (the owner, #146).
- **A service is spoken to at one address, and its body is what it said.** `config.alldebridApi` is AllDebrid's own, replaced only by an address on this computer (`SCIA_ALLDEBRID_API`): the engine does not start with any other. A redirect is not followed. Whether a request succeeded is read in the body — AllDebrid's documentation says both that a refused key comes with a 401 and that it no longer does — and a code that is no answer to what was asked (a link's refusal to a question about the account), a code Scia does not know (looked up in a `Map`: a code is a word from outside), an answer that is not the service's envelope, a date no calendar holds and no answer in time are all `SERVICE_UNAVAILABLE`: nothing is said of the key that the service did not say. Read the service's documentation again before changing its client: do not rely on memory for its endpoints or its codes.
- **A hoster's link is unlocked at the start of its download's run, through `LinkResolver`** ([ADR 0005](../../docs/adr/0005-a-service-resolves-a-link.md); `Integrations` is the adapter, `DownloadManager.#address` the step). What holds:
  - The download is known by the link that was added (`url`). `via` is the service it goes through; `unlockedUrl` is the direct link the service gave — in `state.json`, **never in an answer of the API and never in a log**. A spec reads both.
  - The service is asked once: the link it gave is used again after a pause and after a restart, because asking again can count against what the account is allowed of a host. After a failure, the next attempt asks again.
  - **A direct link that expires is asked for again, keeping the bytes** ([ADR 0022](../../docs/adr/0022-a-direct-link-that-expires.md), #180; `DownloadManager.#runFile`). A 403 or a 410 from the host of a link a service gave — on the way, or when a link kept over a pause or a restart is first asked — and a web page that is not the file whose bytes are kept (`NotTheFile`: at the probe, with bytes kept and another size or validator — `isAnotherFile`, the test of `#adopt`) have the manager ask the service for a new link, ask its host what the file is, and go on from the segments kept; a different file (size, or validator where both answers carry one) starts again from the first byte, as a changed file does (`#adopt`). **Asked again only for a link that brought bytes the download keeps**: a link refused before its first byte — the first one the service gives, or a new one — and a link given again on which the download started from the first byte (another file, a host without ranges) fail the download with their host's answer. No code of the service is taken: AllDebrid documents none. **A web page is never saved over the bytes of a service's link**: from a new link it fails `HTTP_STATUS` with no status; a page with no bytes kept is the file the service unlocked, and a page that is the file whose bytes are kept (a host that labels it `text/html`) goes on from them, a "Retry" included. A link pasted as it stands still fails at once on a 403. The log says `link_unlocked_again`, never the link.
  - A link is a service's when its host name is one of the domains the service lists for the account, or a subdomain of one — never because the name appears somewhere in the address. The list is read when first needed and every six hours; **the last one read is kept between runs** (`alldebrid-hosts.json`, the owner's decision on #7) and gone by when the service does not answer; after a reading that fails, it is used a minute before the service is asked again; it is forgotten when another account or none is connected, and written in turn with connecting and disconnecting, so that a list answered as its key is forgotten does not outlive it. A reading belongs to the key it was asked with: a reading started under the key before is not handed to a download after another key is connected.
  - **No link is started on a guess.** While a connected service has never said which links are its own — the first run after connecting, with the service not answering — a download fails with what the service said, a direct link included: the alternative is a hoster's page saved as the file. And a link that was a service's is never fetched as it stands, also once the service is disconnected.
  - **With no service connected, a file host's link is not fetched as it stands** ([ADR 0006](../../docs/adr/0006-a-file-host-without-a-service.md)): Scia reads AllDebrid's public list of file hosts (`GET /v4/hosts/domains`, no key, `hosts` only — not `streams` or `redirectors`), when a run first needs it and every six hours, in memory, in one request given up on after three seconds (the first link of a run waits on it; a list in hand is used while it is read again); a link on one of those domains or its `www.` — never another subdomain: the servers of a host's files give them to anyone — fails with `SERVICE_NEEDED`. A service connected while it was read decides instead. A list that cannot be read leaves links to go as they stand, as before #49, and is asked again an hour later.
  - The referrer goes to the host of the link that was added, never to the host a service sent Scia to. The name a service gives a file is a name from a host (`fileNameFromHost`), second to the one the direct link's host gives.
  - A refusal of the service is a `DownloadFailure` with a code of its own (`ServiceFailure`, `UnlockFailure`); a code Scia does not know is `SERVICE_UNAVAILABLE`. What can heal — a service that cannot be asked — is asked again a few times, with a wait; what it refuses, it refuses at once. A link the service is preparing is asked about every five seconds, as its documentation says, until it is there, the download is stopped, or thirty minutes have gone by (the owner's decision on #7).
- **A magnet goes to the connected service, and comes back as downloads in its folders** ([ADR 0014](../../docs/adr/0014-magnets-through-a-service.md); `MagnetWatch`, `MagnetService`, the owner's decisions on #137). A magnet is not a download: `Snapshot.magnets`, `magnets` in `state.json` (an older state loads with none). `POST /magnets` (`{ magnets }`, `201`), `POST /magnets/:id/retry`, `DELETE /magnets/:id` — the app's token only. Magnets pasted together are sent in one `POST /v4/magnet/upload`; while any waits, one `POST /v4.1/magnet/status` every five seconds asks where all of them are, on a timer that does not hold the engine open (`unref`, held by no spec); a magnet pasted during a turn is sent when that turn ends; the service's id is kept the moment it is given, so a restart goes on waiting and never sends again. The trees of the magnets ready in a turn (`POST /v4/magnet/files`, one request, 32 deep and 100,000 files at most, http links only — beyond that, or unreadable, `MAGNET_UNREADABLE`; empty, `MAGNET_FAILED`) become downloads with `via` set, each in the folder of its paste / the magnet's name / its folders, every name through `sanitizeFileName` (`magnetFolders`), under the tree's name (`nameKept`) — the magnet's folder the first free name when a file stands under its name; a magnet of one file goes straight into the folder of its paste, with neither the magnet's folder nor its tree's (the owner, #150); then the magnet leaves the list. No service: `SERVICE_NEEDED`. A service that cannot be asked for a moment fails nothing: the next turn asks; a refusal of every magnet at once — not premium, no server — fails the waiting ones with it, at the upload as at the status read, said once and not asked again; a code Scia does not know, said of one magnet, fails it `SERVICE_UNAVAILABLE`, at its upload as at its files — and so does a magnet left out of an answer, or whose state Scia cannot read; the ends the documentation lists for a magnet (`MAGNET_CANT_BOOTSTRAP`, `MAGNET_TOOK_TOO_LONG`, …) are `MAGNET_FAILED`. The magnet itself is in no answer and no log; the log counts.
- **The magnets of the account are read while the page shows them, and only then** ([ADR 0016](../../docs/adr/0016-the-magnets-of-the-account.md); the owner's decisions on #138). `GET /magnets/account` asks AllDebrid once (`/v4.1/magnet/status`, not its live mode) and answers each magnet of the account (`accountMagnetSchema`), with `inScia`; one Scia cannot read is left out. `POST /magnets/account/:id` takes a ready one into Scia's list — `404` for one the account does not have, `409` for one not ready or already in the list, checked after the service answered — with its id and no magnet link (`magnet: null`): the watch collects its files as a pasted one's, nothing is sent, and Retry asks about it again. Both answer `409 SERVICE_NEEDED` with no service connected, and `422 NOT_PREMIUM` for an account that is not. A date of the account no calendar holds is no date (`.catch(null)`, `LAST_SECOND`), never an unreadable entry. One row per magnet of the service: a sent magnet whose id another row already has is let go (`same`), whichever came first. The engine has no timer for the account: the page asks.
- **A magnet copied to the clipboard is sent at once, while a service is connected** ([ADR 0017](../../docs/adr/0017-a-magnet-taken-from-the-clipboard.md); the owner's decision on #139). `POST /magnets/offered` (`{ magnets }`, main's token) adds them as pasted ones (`offerMagnets` → `addMagnets`), the same torrent once; with no service connected (`MagnetService.hasService()`) it answers `[]` and logs `clipboard_magnets_left_out` with a count — never a failed row for a copy.
- **A link that opens into several files waits in the list for the person to choose** ([ADR 0025](../../docs/adr/0025-a-link-that-opens-into-several-files.md); the owner's decisions on #181). What holds:
  - **Which links** are data, in one list (`BUNDLE_SITES` in `bundle-links.ts`): a file host's folder by its domain or `www.` and the beginning of its path, a protector's or a shortener's domain whole — never by a name elsewhere in the address, and never by asking the service first. With a resolver, `add` makes such a link a bundle, not a download: a folder always — with no service connected it fails `SERVICE_NEEDED` — a protector's or a shortener's link only while a service is connected, and as it stands otherwise. **A protector's or a shortener's link the service gives nothing for is fetched as it stands** (the owner, #181): refused, opened into nothing it can get, or its service gone while it waited (`AS_IT_STANDS`), the entry leaves and the link is a download with the referrer and the folder it was added with; a folder fails instead. **A folder copied to the clipboard is offered `ready`** while a service is connected (`hasService`, nothing asked of it), and opened into its files at its Start or at "Start all" (`#queue`), into the folder it was copied for; with none it is left out. A link on a row of its own is in the list for `offer`: not offered again. A protector's or a shortener's link copied is offered as any link is — when its path names a file — and goes through the redirector at its Start.
  - **Opened at once, one at a time** (`LinkResolver.open` beside `unlock`; `AllDebrid.openLink`): `POST /v4/link/redirector`, then `POST /v4/link/infos` for its links a hundred to a request; a link given twice is one file; a file the service says nothing of — an error, an entry that is no http address — is counted (`unavailable`), not listed; an entry of the infos — a file or a refusal — is matched to its link in any order, its scheme aside (`linkOfSchema`, read before what the entry says), else taken by its place; none is `BUNDLE_EMPTY`; past `LINK_FILES_AT_MOST` the first are listed and the rest counted (`leftOut`), never asked about (the owner, #181); any other failure of the question is `SERVICE_UNAVAILABLE`; the redirector's refusals and any other refusal of a link are `BUNDLE_REFUSED`; a key's, a network's and an account's refusals are said as for a link. A restart opens again a link being opened, and keeps the files of one waiting for a choice.
  - **Kept as a magnet is**: `Snapshot.bundles`, `bundles` in `state.json` (an older state loads with none). The entry carries neither the link nor the service's links to its files, and no log carries either; the page names a file by its place. Once started, each file is a download known by the service's link, in the downloads' answers as a magnet's file is (ADR 0014); the link that was pasted stays in `state.json` only. A spec reads the answers before and after the start.
  - **Started by the person**: `POST /bundles/:id/start` with `{ files }` — places, one at least, each once, each listed — the manager's one rule, the contract reads the shape alone (`400` else; `409` for a link not waiting for a choice) — makes those files downloads with `via` set, under the service's names made safe by `fileNameFromHost` when they are listed, kept over the host's (`nameKept`) — with none, the host names the file — in a folder named after the link (`bundleName`: the last part of its path, decoded, without a page's extension, else its host; through `sanitizeFileName`), the first free name beside a file of that name; then the link leaves the list. A link of one file, with nothing it could not get, is that download at once, in the download folder itself. `POST /bundles/:id/retry` asks again a failed one; `DELETE /bundles/:id` forgets it, stopping a question on its way; an answer that lands after it is kept for nothing, and a link removed while it waits is never asked about. `close()` stops the questions and does not wait for them. App's token only.
- **A link whose host answers a web page is read for the video it plays, through `PageReader`** ([ADR 0009](../../docs/adr/0009-the-video-of-a-page.md); `YtDlp` is the adapter, `DownloadManager.#locate` the step). What holds:
  - **yt-dlp reads, the engine downloads.** yt-dlp prints what it found and fetches nothing; the format chosen (`chooseMedia`) is fetched as any file. A link that is a file, or that a service unlocked, is never read.
  - **What yt-dlp is always told is a spec** (`yt-dlp.int.test.ts`): the readers of known sites only (`--use-extractors default,-generic`), no restriction worked around (`--xff never`), no cookie read from a file or a browser, no configuration, cache or plugin of its own, one video, the address last after `--`. A new option is added there first.
  - **Only its `ERROR:` lines are read** (`refusalOf`), never its warnings. A site it does not know, and a page of a site it knows that plays no video **in its own words** (`NO_VIDEO`, quoted from the shipped build) or whose every format is sound alone (decided on what yt-dlp gave, before the containers are kept: a video in a container Scia does not list is `PAGE_FORMAT_UNSUPPORTED`, no format at all `PAGE_UNREADABLE`), are fetched as they stand. 5xx, 429 and a timeout are `PAGE_SITE_BUSY`, matched before the rest; an error no rule knows stays `PAGE_UNREADABLE` — never a page saved where a video was asked for. A new wording becomes a case of `testing/fake-yt-dlp.mjs`, quoted from a real run.
  - **What a site says is checked where it enters**, against the contract: a container of a video (`VIDEO_CONTAINERS`), a height that is a positive whole number or none, the headers that are the site's (`NOT_THE_SITES` are dropped). The video is asked for with those headers and no others, never the page the link was on; `HttpSource` sends `Accept-Encoding: identity` after them.
  - `video` (its `media`, shown, and its `source`: the address and headers) is kept in `state.json` as one value, read whole or not at all, beside a mark that the download is a page's video (`fromPage`), which outlives a `video` refused at load so that the page is read again and never fetched into the file: used again after a pause or a restart, its `source` cleared after a failure so that the page is read again — keeping, for a download whose name is final, the container that name carries. **The video's address is never in an answer of the API and never in a log** (a spec reads both). A page that was being fetched as it stands is never read later: once its name is final, what was decided at its first start stays decided.
  - The file is named after the title, through `sanitizeFileName` (a title is not a path), `video` when the site gives none, with the format's extension.
  - **yt-dlp runs in a folder of its own, with an environment built from nothing** (`environmentOf`): `SystemRoot`, and a temporary folder made for the run inside the system's (which main names, `SCIA_TEMP_DIR`) and removed once the process has closed, however it ended — its build unpacks 30 MB there and leaves it when it is stopped. Never the engine's own environment, which holds the API's token. A read told to stop before yt-dlp started ends at once. **yt-dlp is stopped with its whole tree** — a stop, the timeout, a flood of output (#170): its builds read the page in a second process that holds the output, which ending the first leaves running. On Windows by `taskkill /T /F`, elsewhere as the process group it leads (`detached`); and once Scia has ended it, a process no tree reaches that still holds the output is not waited for more than `OUTPUT_GRACE_MS`.
  - **A stream is fetched as its pieces and made into one mp4 inside the engine** ([ADR 0010](../../docs/adr/0010-a-stream-made-into-an-mp4-inside-scia.md); `HlsTask`): the playlist read by `parsePlaylist` (core), each piece fetched against the one speed limit into `<name>.scia.pieces` (written whole, then renamed; what is there is not asked again; pieces of another quality, by the folder's `variant` label, thrown away), AES-128 opened with the key the playlist names, `SAMPLE-AES` or another key format refused as DRM; fMP4 pieces put behind their init segment, MPEG-TS pieces transmuxed by mux.js through `transmuxer.ts`. No ffmpeg. A live playlist is `PAGE_LIVE` until #121; a stream that changes partway (a discontinuity, another init segment) or whose init segment is named under a key, which encrypts it, is `PAGE_FORMAT_UNSUPPORTED` before a piece is fetched (#123); encrypted pieces behind a clear init segment are downloaded; a piece's length is from nothing to a day. A piece that fails for good ends every connection, and the task waits for them all; pieces and the mp4 are synced before the state says so; the finished size is the mp4's, read from the file. The row's progress is the `timeline` (milliseconds), kept in `state.json`. Specs read the streams of `testing/hls/`, made by `generate.mjs` with ffmpeg by hand — never by a spec.
  - **A picture and its sound offered apart are fetched as two files and joined into one mp4 inside the engine** ([ADR 0021](../../docs/adr/0021-picture-and-sound-joined-into-one-mp4.md); `PairTask`; the owner, #99). What holds:
    - **The choice**: an mp4 picture in H.264 or AV1 (never HEVC or VP9) and an AAC sound in an m4a or mp4, both one file over http(s) and not protected. The best picture has the most lines, H.264 at equal lines; the best sound is in the video's own language, then has the highest bitrate. The pair stands with its picture's lines, after one file and before a stream at equal lines.
    - **The fetch**: each file is a `DownloadTask`, picture first, into `<name>.scia.picture` and `<name>.scia.sound`, on one line of segments (the picture's bytes, then the sound's) that the row shows and `state.json` keeps. Its `source` keeps the sound beside the picture, read whole or not at all.
    - **The join**: `joinPlan` (core) reads the boxes, and `joinIntoMp4` writes the plan, copying the media as it stands. Two fragmented files get their fragments interleaved by time, renumbered and moved; two plain files get one `mdat` and moved chunk offsets (`co64` past 4 GiB). Files it does not join are `PAGE_FORMAT_UNSUPPORTED`, among them a fragmented file with samples in its movie, whose samples the plan would leave out. Boxes that do not hold together, or a box too short for its fields, are `PAGE_UNREADABLE`.
    - **After the join**: the two files are removed once joined, with the download when it is removed, and when a new reading makes the download something else.
    - **The specs**: they read the files of `testing/pair/`, made by `generate.mjs` with ffmpeg by hand, never by a spec.
  - The engine reads pages only when main names a yt-dlp that is there (`SCIA_YT_DLP`); under plain Node it fetches pages as they stand. Specs use `testing/fake-yt-dlp.mjs`, never the real program, and never a real site.
- **A Bunkr album becomes downloads in a folder of its own, read by a reader of Scia's own** ([ADR 0024](../../docs/adr/0024-a-bunkr-album-read-by-scia.md); `Bunkr`, `bunkr-pages.ts`, `DownloadManager.#openAlbum` and `#locateBunkrFile`; the owner's decisions on #228). What holds:
  - **A link is Bunkr's by its host and the shape of its path**: a domain of `BUNKR_DOMAINS` — the one list, Bunkr on a new domain is a new entry — or that domain under `app.`, and `/a/<id>` (an album) or `/f/`, `/v/`, `/i/`, `/d/` and a slug (a file). Any other link of those hosts goes as it stands. **Bunkr's reader decides before any service**: a Bunkr link is never sent to `LinkResolver`, never fails `SERVICE_NEEDED`, and the link Bunkr's API gives is fetched as it stands.
  - **An album is read at the start of its run**: its page (`/a/<id>?advanced=1`) for its title (`og:title`, escaped twice) and `window.albumFiles`, one field a line — anything else in that list, and the album is `ALBUM_UNREADABLE`, never read wrongly. Once read, the row leaves the list and its files take its place in the queue, each a download of its page (`/f/<slug>`, on the host the album was read at), in `<the folder it was added with>/<the title through sanitizeFileName, or the id>` — the first free name beside it when a file stands there, a folder of that name shared — each named as the album names it through `fileNameFromHost` and kept (`nameKept`). **Every address built from a slug is checked to be a Bunkr file's page again** (`bunkrLinkOf`): `.` and `..` are other paths once parsed, and such an album is `ALBUM_UNREADABLE`. A stop while the page is read ends the read: nothing is added. The log counts the files, never the album.
  - **A file is read again at every run, and nothing of it is kept**: its page for `data-file-id` (and its `<h1>`, the name of a file pasted by itself, through `fileNameFromHost`), then `POST` to the API with `{ id }`, `Referer`/`Origin` of `get.bunkrr.su`, and the link it gives — base64, XOR'd with `SECRET_KEY_<hour>` when `encrypted` is `true` (the owner's decision on #228) — fetched with that `Referer`. A link that lands on `maint.mp4`/`maintenance-vid.mp4` is `PAGE_SITE_BUSY`; a link refused for good (a 4xx), at its probe or partway, or answering a web page, is `ALBUM_LINK_FAILED` with its status — a busy server (what `HttpSource` marks retryable) and a range ignored (a 200) keep `HTTP_STATUS` — whose sentence says that Retry asks the site for a new one — never a page saved as the file, never the sentence of a pasted link.
  - **What a host writes is read in linear time**: no regular expression that backtracks over it (a field by its first `:`; a heading's attributes cannot pass a `<`). The engine has one thread; a spec times a hostile line and a page of `<h1 ` never closed.
  - **Respect the hosts**: Scia's own user agent; no cookie; a 403 (Cloudflare's challenge too) is `ALBUM_REFUSED`, never solved or tried on another domain; 404/410 and the API's 400 `ALBUM_GONE`; an empty album `ALBUM_EMPTY`. **What can heal is asked again, as everywhere in the engine**: a 5xx, a 429, a dropped connection, no answer in 30 s — three times more at most, after 1, 2 and 4 s (`retryDelayMs`) or the site's `Retry-After` when longer; one asking for more than a minute is not asked again; then `PAGE_SITE_BUSY` or `NETWORK`. Pages are bounded (16 MB, 2 MB, 64 KB for the API's answer); a page's redirect is followed five times at most and only to a host of the list, the API's never.
  - **A run points the reader at a host on this computer with `SCIA_BUNKR`** (main's `--bunkr=`): Bunkr's links are that host's name, its API the same path there; the engine does not start with any other address. **The specs** use `testing/bunkr-server.ts`, which answers in the shapes gallery-dl's source reads, never Bunkr itself; the E2E suite starts the built app with it (`bunkr.e2e.test.ts`).
- **The links main read on the clipboard are offered, and the engine keeps what it knows** ([ADR 0012](../../docs/adr/0012-links-taken-from-the-clipboard.md); `DownloadManager.offer`, `offered-links.ts`): `POST /downloads/offered`, the app's token only. A link is kept when the last name of its path is a file's that is not an image (`fileKindOfName`), when it is one video's page on a site of `VIDEO_SITES` (by host and shape of path: a home, a channel, a list or a search is not one video), or when `LinkResolver.serviceFor` takes it or says it needs a service — within `OFFER_HOST_LIMIT_MS`; what the service cannot say is left out. A link whose address is already in the list, whatever its state, is not added again — checked after the wait, so two offers together add it once. What is kept is added `ready`: `nextToStart` never starts it, nothing is asked of its host — but a video's title (below) — it has no part file; `POST /downloads/:id/start` (409 for any other state) and `POST /downloads/start-ready` put it in the queue. The log says how many links and how many were added, never which. `watchClipboard` is a setting, off by default, and every `Snapshot` carries it for main.
  - **A video's page added `ready` is read at once for its title alone** (ADR 0012, its amendment; the owner, #285; `PageReader.readTitle`, `DownloadManager.#readTitles`): the same rules as a read (`--print %(title)j` and `--flat-playlist` in place of `--dump-single-json`, a spec), 30 s and 64 KiB at most, one line made text and cut to `TITLE_MOST_CHARS` by `titleOfVideo`. A title takes a turn only while yt-dlp reads fewer pages — titles and downloads' pages together (`#pageReads`) — than `maxConcurrentDownloads`; a download never waits for one: its page about to be read takes the turn of the newest title, which is stopped and waits again first in line (`#yieldToPage`). Start, "Start all" and Remove stop the read, and a late answer is kept nowhere. `close()` stops every title before its first wait (`#stopping`), starts none after, and waits for each read it stopped (`#titleReads`), so that yt-dlp has ended and its folder is gone when the engine exits: a spec's reader of titles must end at its signal, or `close()` waits for ever. Read once: `title` is in `state.json`, in the answers only until the file is named, and a failure keeps the address. The log says `ready_title_read` / `ready_title_not_read` with the id and a code, never the address or the title.
- **The shipped yt-dlp is brought up to date by the engine** ([ADR 0011](../../docs/adr/0011-yt-dlp-kept-up-to-date.md); `YtDlpUpdates`), only when main says which release it shipped and its build's name (`SCIA_YT_DLP_VERSION`, `SCIA_YT_DLP_ASSET`). What holds:
  - **A build is used only when `SHA2-256SUMS.sig` is a good signature of the release's sums by yt-dlp's key** (`yt-dlp-signing-key.ts`; a spec checks it against the fingerprint yt-dlp publishes), made no earlier than the day the release is named after, **and its bytes have the sha256 those sums give it**. `openpgp.ts` reads one kind of signature — version 4, of a binary document, RSA, SHA-256/384/512, dated, with no critical condition it does not know — and anything else is no signature. A spec reads a real release of yt-dlp (`testing/yt-dlp-2026.10.26/`); the others sign with a key made for them (`testing/openpgp-signer.ts`).
  - **The shipped build is never written to.** A build taken is kept under the profile, `engine/yt-dlp/<version>/`, with `state.json` (the last check, the build and its sha256); its bytes are read against that sha256 at every start, and it is dropped once Scia ships a yt-dlp as new. Whatever else is in the folder is removed at the start, never while a read may run it.
  - **The updater never stops the engine**: an entry it cannot remove is logged and left for a later start, and an updater that cannot be opened (`openYtDlpUpdates`) is logged and leaves the shipped build reading pages. A stop is heard at every wait, also one that came before the wait began.
  - **A read runs the build in use when it starts** (`YtDlp`'s `command` is asked at each read): a read under way keeps its own.
  - **Once a day, an hour after a check that could not be made**: the first once the engine listens, when the last is a day old. A refusal is final for that release until the next day's check. The time of the last check is kept between runs.
  - **The build is fetched only while no download runs or waits** (`DownloadManager.isBusy`, `onBusyChange`), and given up — its part removed — when one starts, then fetched again whole.
  - **yt-dlp's releases are read at github.com** (`/releases/latest`, without following its redirect; `/releases/download/<tag>/<name>`), replaced only by an address on this computer (`SCIA_YT_DLP_RELEASES`). Specs use `testing/yt-dlp-releases-server.ts`, which answers as github.com does and misbehaves when told to; never GitHub.
- **Every completed download leaves the list in one request** (`POST /downloads/clear-completed`, the app's token only; `DownloadManager.clearCompleted`; #215): `204`, one change and one save however many rows go — a `DELETE` of each would save the list once per row — the files kept on the disk, as a single row's removal keeps a finished file; nothing that is not completed is touched, and with none completed nothing changes and nothing is saved.
- **Two tokens, two scopes** ([ADR 0002](../../docs/adr/0002-browser-extension-pairing.md)): the app's token (new at every launch) opens every route; the extension's token (persisted in the profile's `engine/extension-token`; Settings offers it again once the extension is published, #152) opens `EXTENSION_ROUTES` and nothing else. A new route is app-only unless the ADR is amended.
- **Only the engine's own host is answered** (`127.0.0.1:<port>` or `localhost:<port>`), and no CORS header is ever sent: a web page can neither read the API nor reach it under another name.
- **The environment is the configuration** (`config.ts`): `SCIA_*` variables given by main, never a file beside the executable.
- **Errors cross the API as `{ error: { code, message } }`** with a code from `ApiErrorCode`; the text a person reads lives in the renderer.

## Testing

- `*.test.ts` — pure pieces (config), and the throttle on a clock and timers the spec moves.
- `*.int.test.ts` — `DownloadTask`, `HttpSource` and `DownloadManager` against `testing/range-server.ts`, a real HTTP host on a free port, and a temp folder. Compare bytes, not counters.
- `*.feature.test.ts` — the API through `app.request()`: every route's token, scope and status code.
- A service is a local host too: `testing/alldebrid-server.ts` answers as AllDebrid's documentation says its API does, refusals included, and misbehaves when told to (`misbehave`). The client, `Integrations`, the routes and a pasted link from the paste to the file (`unlock.int.test.ts`) are proven against it. Every key in a spec is made up: nobody's real key comes near a spec or a run.
- Timing in tests comes from `until(condition)`, never from a fixed sleep; retry delays and the idle timeout are injected (`retryDelayMs`, `idleTimeoutMs`). A rate is proven against a host that does not pause (`chunkDelayMs` unset) and counted in bytes.
