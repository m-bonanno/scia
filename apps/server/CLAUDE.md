# Scia — Engine CLAUDE.md (`apps/server`)

Loaded when working under `apps/server/`. **Extends** the root `CLAUDE.md`; wins for the engine.

The engine downloads. It is a plain Node process: Electron forks it as a `utilityProcess`, the tests and `npm run dev` run it under Node. **It never imports `electron`** (ESLint enforces it).

```
main.ts            wiring: config → integrations → store → manager → Hono on 127.0.0.1
app.ts             the HTTP API (/api/v1), its two tokens, the renderer's static files
download-manager   the queue, the names, the state on disk, what a pause/remove/shutdown means
download-task      one download: connections, ranges, retries, writes
throttle           the speed limit as connections meet it: who waits, and who is woken
remote-source      the PORT a download reaches its bytes through
http-source        its one adapter today (node:http/https)
state-store        state.json, written whole and renamed into place
origin-mark        the mark a finished file carries of having come from the network
offered-links      which links copied to the clipboard are files or videos' pages Scia knows
integrations       the services Scia is connected to: the key of each, what each says of its account
alldebrid          AllDebrid's API, as far as Scia uses it
key-vault          the PORT the key of a service is kept through; main keeps it
link-resolver      the PORT a debrid service plugs into: is this link a service's, and what is behind it
page-reader        the PORT a reader of sites plugs into: what video a page plays
yt-dlp             its adapter: yt-dlp run once per page, its JSON read
yt-dlp-updates     the shipped yt-dlp brought up to date, at most once a day, from its signed releases
yt-dlp-releases    yt-dlp's releases on github.com: the latest one's name, its files
openpgp            as much of OpenPGP as yt-dlp's signature of its sums takes, over node:crypto
media-choice       which of a page's formats the engine fetches, or why none
hls-task           a page's HLS stream: its pieces fetched, opened, made into one mp4
transmuxer         what the engine uses of mux.js, typed: MPEG-TS into fragmented mp4
```

## Rules

- **Ports where there is a seam.** `RemoteSource` (probe + open a range) is what HLS and any future source implement; `LinkResolver` is the step before it, which a debrid service plugs into; `StateStore` is what a database would replace. Do not add a port without a second implementation or a test that needs the seam.
- **The part file is the truth about bytes; `state.json` never claims more than the disk holds.** A checkpoint syncs the file first, then writes the state. A crash re-downloads a little; it never corrupts.
- **A file is never overwritten.** Names are made unique against the folder and against the downloads still on their way there, and checked again when the part file is renamed.
- **A finished file carries its system's mark of what came from the network** ([ADR 0003](../../docs/adr/0003-the-mark-of-a-downloaded-file.md), `origin-mark.ts`): on Windows the `Zone.Identifier` stream, with the zone and never the address the file came from. It is written on the part file, before the name is looked at and the file renamed: the file never stands under its name unmarked, and nothing waits between "is the name free?" and the rename. A disk that refuses the stream gets its file all the same, and a `mark_refused` with its id in the log: a download does not fail for a mark.
- **Names from a host are hostile.** They pass through `sanitizeFileName` and lose any path before they touch the disk. A test covers every new source of names.
- **Retry what can heal, not what cannot**: a dropped connection, a 5xx, a 429 retry with backoff; a 404 or a 403 fail at once and say so. A 204 to a range is a busy answer too: a direct link of AllDebrid gave it for parts of a file it had not fetched yet, and the same ranges a moment later (#65). And a 200 to the first byte that carries only that byte is a range answered with the wrong status, not a file of one byte: the length is asked again without a range.
- **`Accept-Encoding: identity` always.** A compressed body does not match the ranges asked for.
- **One speed limit for everything** (`Throttle`, one in `DownloadManager`, over the `Pacer` of `@scia/core`). **A connection reads only against room booked before the read**: before it asks its host for a range it books one read's worth (64 KB, or what is left of its range when that is less) and waits its turn; before every read after that, when what it has booked no longer covers the largest read it has made, it books up to a whole read again. When it is done — finished, failed, paused, removed — it settles: what it booked and did not read is given back. A download that is paused or removed leaves nothing owed. A host is held back by not being read from; no byte that was read is thrown away.
  - **Nothing is read that the limit has not made room for, from the first byte, but for three things, each with its bound**:
    1. when a limit is set or lowered, each connection in the middle of a read finishes that read — one read at most — and pays for it before its next;
    2. a read larger than any its connection has made before passes what was booked by the difference — less than one read over the connection's whole life — and is paid for before the next;
    3. a booking may start up to 50 ms in the past, so that a wait that ends late is caught up: the limit is passed by no more than 50 ms' worth of it, and nothing beyond that is ever caught up. A system's timer may fire fifteen milliseconds late, which under a high limit is many reads' turns.
  - "Read" is what the engine takes from a connection. What the host has sent ahead of that — in the system's buffers and in Node's — is not counted: it is there once for each connection, it is not a rate, and it is how any limit that holds a host back by not reading works.
  - Under a limit the connections of a download open one after the other, as the limit makes room, and a connection's turn comes round every connections × 64 KB ÷ the limit: 40 s at the most Settings allows (160 connections, 256 KB/s). Over an encrypted connection a read is a record of 16 KB: one booking covers four.
  - **A connection held back is not a silent host.** `HttpSource` times a host's silence only while a read is waiting for it — never on the socket, which is quiet whenever Scia is not reading. That timer was also what ended an answer nobody read: a redirect's answer is closed, not drained, and what `open` answers is read at once (`remote-source.ts`).
  - It runs on a clock that never steps (`performance.now`), not the system's: a clock set back an hour would be an hour without a byte.
  - Changing or lifting it wakes whoever is waiting, to book again under the new limit; what was booked with the old one is forgotten. A download that is paused, removed or stopped does not wait on the limit: the wait ends with its signal.
  - **A limit is tried at both ends of the menu, against a host that does not pause, in bytes.** Three shapes of this were wrong, each invisible to the runs made of it: paid after the read, every connection's first read passed unpaid and stayed owed when its download was removed; booked only when nothing was left, the couple of hundred bytes an answer's headers leave of a booking let a whole read through, twice the limit while connections opened — hidden by a test host that paused between pieces; and with a wait before every read and none made up, a download under 25 MB/s got a third of it — hidden by runs that all sat between 256 KB/s and 2 MB/s.
- **`GET /events` is never silent for long** (`EVENTS_KEEP_ALIVE_MS` in `@scia/contracts`): with nothing to send, and between two lists, the stream writes a comment, which a reader of events passes over. Whoever listens can tell an engine with nothing to say from one that stopped talking, and a client that ends an answer after minutes without a byte — Node's `fetch`, after five — never meets one. The wait for a change is called off when the listener goes (`nextChange(since, gone)`): a stream that closed leaves nothing waiting in the manager.
- **`state.json` takes a new setting with a default** (`state-store.ts`): a file written before the setting existed loads, with the default — and so does one whose stored value the bounds of today refuse. A state that does not parse is set aside as `.unreadable` and the engine starts empty — so a setting added without a default, or a bound tightened later, would lose every download in the list.
- **The theme of the interface is a setting** (`theme`, one of `Theme` in `@scia/contracts/theme`; the page patches it), and **the page is served wearing it**: `data-theme` is written on the `<html>` of `index.html` at every request, so the page's first paint is in the theme, with no script and no answer to wait for. A state that names a theme this version does not have loads with the default one.
- **The download folder has a route of its own** (`PUT /settings/download-directory`, the app's token only): main names it after the person chose it in the system's dialog. It is not among the settings the page patches, so no type lets the page send a path. The engine takes an absolute path, keeps it as the system names it (`resolve`), makes the folder, and refuses one it cannot make or write to, leaving the settings as they were. **Writing is proven by writing** — a file of Scia's own made in the folder and removed — never by asking the system: on Windows `access(folder, W_OK)` says yes for every folder that exists. A download keeps the folder it was added with.
- **The key of a service is in the engine's memory and in the vault, and nowhere else** ([ADR 0004](../../docs/adr/0004-the-key-of-a-service.md)): never in `state.json`, in a log, in an error, in an address, or in an answer of the API — no route says a key back. `KeyVault` is the port: `ParentVault` asks main, which keeps the key sealed by the system; `MemoryVault` is what plain Node has, and keeps it as long as the process. A key is kept only after its service accepted it, and leaves the vault before it is forgotten: one that stayed would connect Scia again at its next start. A spec that says "never in the log" reads every line that was logged.
- **The routes of a service are three, for the app's token alone**: `GET /integrations`, `PUT /integrations/:id` with `{ apiKey }`, `DELETE /integrations/:id`. `400 INVALID_REQUEST` for what cannot be a key, before the service is asked; `422` with the service's refusal (`KEY_REFUSED`, `KEY_BLOCKED`, `ACCOUNT_BANNED`, `NETWORK_REFUSED` — AllDebrid's `NO_SERVER`, a server or a VPN it does not serve); `502 SERVICE_UNAVAILABLE` when it could not be asked; `500 KEY_NOT_KEPT` when the system will not keep the key; `404` for a service Scia does not know; `204` for a disconnection. Connecting and disconnecting happen one at a time, and a write that was given up on is undone: the vault is put back as it was. A listing waits two seconds at most for the service to say whose account it is, then answers what it knows.
- **A service is spoken to at one address, and its body is what it said.** `config.alldebridApi` is AllDebrid's own, replaced only by an address on this computer (`SCIA_ALLDEBRID_API`): the engine does not start with any other. A redirect is not followed. Whether a request succeeded is read in the body — AllDebrid's documentation says both that a refused key comes with a 401 and that it no longer does — and a code that is no answer to what was asked (a link's refusal to a question about the account), a code Scia does not know (looked up in a `Map`: a code is a word from outside), an answer that is not the service's envelope, a date no calendar holds and no answer in time are all `SERVICE_UNAVAILABLE`: nothing is said of the key that the service did not say. Read the service's documentation again before changing its client: do not rely on memory for its endpoints or its codes.
- **A hoster's link is unlocked at the start of its download's run, through `LinkResolver`** ([ADR 0005](../../docs/adr/0005-a-service-resolves-a-link.md); `Integrations` is the adapter, `DownloadManager.#address` the step). What holds:
  - The download is known by the link that was added (`url`). `via` is the service it goes through; `unlockedUrl` is the direct link the service gave — in `state.json`, **never in an answer of the API and never in a log**. A spec reads both.
  - The service is asked once: the link it gave is used again after a pause and after a restart, because asking again can count against what the account is allowed of a host. After a failure, the next attempt asks again.
  - A link is a service's when its host name is one of the domains the service lists for the account, or a subdomain of one — never because the name appears somewhere in the address. The list is read when first needed and every six hours; **the last one read is kept between runs** (`alldebrid-hosts.json`, the owner's decision on #7) and gone by when the service does not answer; after a reading that fails, it is used a minute before the service is asked again; it is forgotten when another account or none is connected, and written in turn with connecting and disconnecting, so that a list answered as its key is forgotten does not outlive it. A reading belongs to the key it was asked with: a reading started under the key before is not handed to a download after another key is connected.
  - **No link is started on a guess.** While a connected service has never said which links are its own — the first run after connecting, with the service not answering — a download fails with what the service said, a direct link included: the alternative is a hoster's page saved as the file. And a link that was a service's is never fetched as it stands, also once the service is disconnected.
  - **With no service connected, a file host's link is not fetched as it stands** ([ADR 0006](../../docs/adr/0006-a-file-host-without-a-service.md)): Scia reads AllDebrid's public list of file hosts (`GET /v4/hosts/domains`, no key, `hosts` only — not `streams` or `redirectors`), when a run first needs it and every six hours, in memory, in one request given up on after three seconds (the first link of a run waits on it; a list in hand is used while it is read again); a link on one of those domains or its `www.` — never another subdomain: the servers of a host's files give them to anyone — fails with `SERVICE_NEEDED`. A service connected while it was read decides instead. A list that cannot be read leaves links to go as they stand, as before #49, and is asked again an hour later.
  - The referrer goes to the host of the link that was added, never to the host a service sent Scia to. The name a service gives a file is a name from a host (`fileNameFromHost`), second to the one the direct link's host gives.
  - A refusal of the service is a `DownloadFailure` with a code of its own (`ServiceFailure`, `UnlockFailure`); a code Scia does not know is `SERVICE_UNAVAILABLE`. What can heal — a service that cannot be asked — is asked again a few times, with a wait; what it refuses, it refuses at once. A link the service is preparing is asked about every five seconds, as its documentation says, until it is there, the download is stopped, or thirty minutes have gone by (the owner's decision on #7).
- **A link whose host answers a web page is read for the video it plays, through `PageReader`** ([ADR 0009](../../docs/adr/0009-the-video-of-a-page.md); `YtDlp` is the adapter, `DownloadManager.#locate` the step). What holds:
  - **yt-dlp reads, the engine downloads.** yt-dlp prints what it found and fetches nothing; the format chosen (`chooseMedia`) is fetched as any file. A link that is a file, or that a service unlocked, is never read.
  - **What yt-dlp is always told is a spec** (`yt-dlp.int.test.ts`): the readers of known sites only (`--use-extractors default,-generic`), no restriction worked around (`--xff never`), no cookie read from a file or a browser, no configuration, cache or plugin of its own, one video, the address last after `--`. A new option is added there first.
  - **Only its `ERROR:` lines are read** (`refusalOf`), never its warnings. A site it does not know, and a page of a site it knows that plays no video **in its own words** (`NO_VIDEO`, quoted from the shipped build) or whose every format is sound alone (decided on what yt-dlp gave, before the containers are kept: a video in a container Scia does not list is `PAGE_FORMAT_UNSUPPORTED`, no format at all `PAGE_UNREADABLE`), are fetched as they stand. 5xx, 429 and a timeout are `PAGE_SITE_BUSY`, matched before the rest; an error no rule knows stays `PAGE_UNREADABLE` — never a page saved where a video was asked for. A new wording becomes a case of `testing/fake-yt-dlp.mjs`, quoted from a real run.
  - **What a site says is checked where it enters**, against the contract: a container of a video (`VIDEO_CONTAINERS`), a height that is a positive whole number or none, the headers that are the site's (`NOT_THE_SITES` are dropped). The video is asked for with those headers and no others, never the page the link was on; `HttpSource` sends `Accept-Encoding: identity` after them.
  - `video` (its `media`, shown, and its `source`: the address and headers) is kept in `state.json` as one value, read whole or not at all, beside a mark that the download is a page's video (`fromPage`), which outlives a `video` refused at load so that the page is read again and never fetched into the file: used again after a pause or a restart, its `source` cleared after a failure so that the page is read again — keeping, for a download whose name is final, the container that name carries. **The video's address is never in an answer of the API and never in a log** (a spec reads both). A page that was being fetched as it stands is never read later: once its name is final, what was decided at its first start stays decided.
  - The file is named after the title, through `sanitizeFileName` (a title is not a path), `video` when the site gives none, with the format's extension.
  - **yt-dlp runs in a folder of its own, with an environment built from nothing** (`environmentOf`): `SystemRoot`, and a temporary folder made for the run inside the system's (which main names, `SCIA_TEMP_DIR`) and removed once the process has closed, however it ended — its build unpacks 30 MB there and leaves it when it is stopped. Never the engine's own environment, which holds the API's token. A read told to stop before yt-dlp started ends at once.
  - **A stream is fetched as its pieces and made into one mp4 inside the engine** ([ADR 0010](../../docs/adr/0010-a-stream-made-into-an-mp4-inside-scia.md); `HlsTask`): the playlist read by `parsePlaylist` (core), each piece fetched against the one speed limit into `<name>.scia.pieces` (written whole, then renamed; what is there is not asked again; pieces of another quality, by the folder's `variant` label, thrown away), AES-128 opened with the key the playlist names, `SAMPLE-AES` or another key format refused as DRM; fMP4 pieces put behind their init segment, MPEG-TS pieces transmuxed by mux.js through `transmuxer.ts`. No ffmpeg. A live playlist is `PAGE_LIVE` until #121; a stream that changes partway (a discontinuity, another init segment) or whose init segment is named under a key, which encrypts it, is `PAGE_FORMAT_UNSUPPORTED` before a piece is fetched (#123); encrypted pieces behind a clear init segment are downloaded; a piece's length is from nothing to a day. A piece that fails for good ends every connection, and the task waits for them all; pieces and the mp4 are synced before the state says so; the finished size is the mp4's, read from the file. The row's progress is the `timeline` (milliseconds), kept in `state.json`. Specs read the streams of `testing/hls/`, made by `generate.mjs` with ffmpeg by hand — never by a spec.
  - The engine reads pages only when main names a yt-dlp that is there (`SCIA_YT_DLP`); under plain Node it fetches pages as they stand. Specs use `testing/fake-yt-dlp.mjs`, never the real program, and never a real site.
- **The links main read on the clipboard are offered, and the engine keeps what it knows** ([ADR 0012](../../docs/adr/0012-links-taken-from-the-clipboard.md); `DownloadManager.offer`, `offered-links.ts`): `POST /downloads/offered`, the app's token only. A link is kept when the last name of its path is a file's that is not an image (`fileKindOfName`), when it is one video's page on a site of `VIDEO_SITES` (by host and shape of path: a home, a channel, a list or a search is not one video), or when `LinkResolver.serviceFor` takes it or says it needs a service — within `OFFER_HOST_LIMIT_MS`; what the service cannot say is left out. A link whose address is already in the list, whatever its state, is not added again — checked after the wait, so two offers together add it once. What is kept is added `ready`: `nextToStart` never starts it, nothing is asked of its host, it has no part file; `POST /downloads/:id/start` (409 for any other state) and `POST /downloads/start-ready` put it in the queue. The log says how many links and how many were added, never which. `watchClipboard` is a setting, off by default, and every `Snapshot` carries it for main.
- **The shipped yt-dlp is brought up to date by the engine** ([ADR 0011](../../docs/adr/0011-yt-dlp-kept-up-to-date.md); `YtDlpUpdates`), only when main says which release it shipped and its build's name (`SCIA_YT_DLP_VERSION`, `SCIA_YT_DLP_ASSET`). What holds:
  - **A build is used only when `SHA2-256SUMS.sig` is a good signature of the release's sums by yt-dlp's key** (`yt-dlp-signing-key.ts`; a spec checks it against the fingerprint yt-dlp publishes), made no earlier than the day the release is named after, **and its bytes have the sha256 those sums give it**. `openpgp.ts` reads one kind of signature — version 4, of a binary document, RSA, SHA-256/384/512, dated, with no critical condition it does not know — and anything else is no signature. A spec reads a real release of yt-dlp (`testing/yt-dlp-2026.10.26/`); the others sign with a key made for them (`testing/openpgp-signer.ts`).
  - **The shipped build is never written to.** A build taken is kept under the profile, `engine/yt-dlp/<version>/`, with `state.json` (the last check, the build and its sha256); its bytes are read against that sha256 at every start, and it is dropped once Scia ships a yt-dlp as new. Whatever else is in the folder is removed at the start, never while a read may run it.
  - **The updater never stops the engine**: an entry it cannot remove is logged and left for a later start, and an updater that cannot be opened (`openYtDlpUpdates`) is logged and leaves the shipped build reading pages. A stop is heard at every wait, also one that came before the wait began.
  - **A read runs the build in use when it starts** (`YtDlp`'s `command` is asked at each read): a read under way keeps its own.
  - **Once a day, an hour after a check that could not be made**: the first once the engine listens, when the last is a day old. A refusal is final for that release until the next day's check. The time of the last check is kept between runs.
  - **The build is fetched only while no download runs or waits** (`DownloadManager.isBusy`, `onBusyChange`), and given up — its part removed — when one starts, then fetched again whole.
  - **yt-dlp's releases are read at github.com** (`/releases/latest`, without following its redirect; `/releases/download/<tag>/<name>`), replaced only by an address on this computer (`SCIA_YT_DLP_RELEASES`). Specs use `testing/yt-dlp-releases-server.ts`, which answers as github.com does and misbehaves when told to; never GitHub.
- **Two tokens, two scopes** ([ADR 0002](../../docs/adr/0002-browser-extension-pairing.md)): the app's token (new at every launch) opens every route; the extension's token (persisted, shown in settings) opens `EXTENSION_ROUTES` and nothing else. A new route is app-only unless the ADR is amended.
- **Only the engine's own host is answered** (`127.0.0.1:<port>` or `localhost:<port>`), and no CORS header is ever sent: a web page can neither read the API nor reach it under another name.
- **The environment is the configuration** (`config.ts`): `SCIA_*` variables given by main, never a file beside the executable.
- **Errors cross the API as `{ error: { code, message } }`** with a code from `ApiErrorCode`; the text a person reads lives in the renderer.

## Testing

- `*.test.ts` — pure pieces (config), and the throttle on a clock and timers the spec moves.
- `*.int.test.ts` — `DownloadTask`, `HttpSource` and `DownloadManager` against `testing/range-server.ts`, a real HTTP host on a free port, and a temp folder. Compare bytes, not counters.
- `*.feature.test.ts` — the API through `app.request()`: every route's token, scope and status code.
- A service is a local host too: `testing/alldebrid-server.ts` answers as AllDebrid's documentation says its API does, refusals included, and misbehaves when told to (`misbehave`). The client, `Integrations`, the routes and a pasted link from the paste to the file (`unlock.int.test.ts`) are proven against it. Every key in a spec is made up: nobody's real key comes near a spec or a run.
- Timing in tests comes from `until(condition)`, never from a fixed sleep; retry delays and the idle timeout are injected (`retryDelayMs`, `idleTimeoutMs`). A rate is proven against a host that does not pause (`chunkDelayMs` unset) and counted in bytes.
