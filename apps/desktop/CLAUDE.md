# Scia — Desktop CLAUDE.md (`apps/desktop`)

Loaded when working under `apps/desktop/`. **Extends** the root `CLAUDE.md`; wins for Electron-shell work.

## Process model

```
main (Electron: lifecycle, supervision, the window, the tray, the system's notifications, the shell's file manager, the keys of services)
 ├─ utilityProcess → apps/server (Hono on 127.0.0.1:<port>, the downloads)
 └─ BrowserWindow → loads http://127.0.0.1:<port>/ (renderer served by the engine)
       └─ preload (sandboxed, CommonJS) → window.scia
```

## The rule that shapes everything: pure engine + thin IO adapter

| Piece       | Holds                                                                                       | Tested by                  |
| ----------- | ------------------------------------------------------------------------------------------- | -------------------------- |
| **Engine**  | decisions with zero Electron: restart backoff, paths from a root, argv, the env, colours    | Vitest unit, no Electron   |
| **Adapter** | the IO the engine describes: `utilityProcess.fork`, `BrowserWindow`, `shell`, `safeStorage` | the real app (`npm start`) |

**`src/engine/**` never imports `electron`** — ESLint enforces it. A new capability = engine + spec first, adapter second, wiring in `main.ts` third.

## Hard rules

- **Security defaults are non-negotiable**: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, no `webviewTag`. Navigation away from the app's origin is blocked and every `window.open` denied. The session refuses every permission except `clipboard-sanitized-write` for the app's own origin (`engine/page-permissions.ts`). The packaged exe sets its fuses in `electron-builder.yml`.
- **The preload is CommonJS.** A sandboxed preload cannot be ESM — it is silently not loaded. Keep its output `.cjs`.
- **`window.scia` is the whole bridge, and it stays tiny**: the API token, the version, the platform, `revealDownload(id)`, `openDownload(id)`, `chooseDownloadFolder()`, `themeChanged()`. Main answers a channel only through `MainWindow.answer(name, handler)`, which refuses any sender but the app's page. Adding a member means editing, in one PR: the preload, the main handler, `BridgeChannel` in `@scia/contracts/bridge`, and the renderer's `SciaBridge`. Never a generic `invoke(channel, …)`.
- **Main never takes a path or a URL from the page.** The page names a download by id; main asks the engine for its file (`engine/download-location.ts`) and only then calls `shell`.
- **The folder new downloads go to is chosen in the system's own dialog, which main shows** (`MainWindow.pickFolder`), and main tells the engine (`engine/download-folder.ts`): the page asks with no argument and reads back what the engine kept. Main answers what became of the folder as a value (`FolderChange` in `@scia/contracts/bridge`: changed, kept, refused) and rejects only for what is not about a folder — an engine that fails or is silent — so that the page never blames a folder nobody chose. One dialog at a time: an ask that arrives while one is open gets that one's answer (`oneAtATime`). The bound on the engine's answers is not a bound on the person, who takes the time they need in the dialog.
- **Main keeps the keys of the connected services, sealed by the system** ([ADR 0004](../../docs/adr/0004-the-key-of-a-service.md); `engine/key-vault.ts`, `key-store.ts`). The engine asks on its own channel, never the page on the bridge: `startServer` answers the engine's messages from its first moment, because the engine asks for its keys before it listens. Main answers only for a name that is a service's id — the name becomes a file's name — keeps a key only where the system protects it (`isProtectedStorage`: on Linux Electron says it can encrypt with no keyring there), and never fails for it: a refusal is an answer. It does one thing at a time, in the order asked: a write that is slow never lands after the removal that followed it. A key is never in main's log.
- **The window's own colours are the theme's** (`WINDOW_COLOURS` in `@scia/contracts/theme`, `engine/title-bar.ts`): its background before the page paints, and the system's buttons the page leaves room for. Main asks the engine which theme the person chose (`engine/window-theme.ts`) before the window loads the page — at the start and after every restart of the engine — and again when the page says that it changed; the page says only that, and never which. The variant, light or dark, is the system's (`nativeTheme`). An engine that does not say leaves the window as it is, and a line in the log.
- **`ipcMain.handle` only.** No `sendSync`.
- **The engine's environment is a whitelist** (`engine/server-env.ts`). Never spread `process.env` into a child.
- **Supervision** (`engine/server-supervisor.ts`): the window follows the engine once it says `ready`; an engine that does not start the first time is given up on at once; one that exits by itself later is started again with a growing wait, and given up on after too many failures in a row. Either way the person is told, with the log's path, in words that depend on the cause (`engine/engine-failure.ts`): a cause to remove is named only where one is known — the port, for an engine that never started.
- **Quitting never hangs**: the window hides at once, the engine is asked to stop and write its state, and is stopped anyway after `STOP_LIMIT_MS`. An engine still starting when the quit is asked ends with the process, which exits as soon as there is nothing to stop; `ServerSupervisor`, on its own, also stops rather than watches an engine that arrives after `stop()`, and counts no failure once it was asked to stop.
- **Main never waits on the engine without a bound** (`ENGINE_ANSWER_LIMIT_MS`): an engine can be alive and silent, and whatever asked — a close, the tray, "Show in folder" — must get an answer or a refusal. The one thing main keeps open is the engine's stream of changes, which has bounds of its own (below).
- **Closing the window is a question, not an order** (`engine/close-policy.ts`, `WindowCloser`). `MainWindow` prevents every close and hands it to main. The window **hides at once**; then main asks the engine once what it is doing, and Scia stays hidden while downloads are running or waiting **and** a tray exists, and quits otherwise — also when the engine says nothing in time. The window hides at every close; the decision is one at a time, none once a quit has begun, and none against a window the person brought back while the engine was asked.
- **A quit never goes through the window.** The `before-quit` handler is registered before the first wait of `boot`, so it exists before anything that can ask for a quit (the tray, the system); it refuses Electron's own quit every time, stops the engine, and ends the process with `app.exit`. Closing or destroying the window to quit would be cancelled by the close handler and asked again, in a loop.
- **The tray asks, it never polls** (`tray.ts`, `engine/tray-presentation.ts`, `engine/download-activity.ts`). The tooltip counts the downloads only while the pointer is on the icon, when the count was just read, and goes back to the plain name when it leaves; an answer that comes back after the pointer has left, or for an earlier visit, is not said (`engine/pointer-tooltip.ts`): a count left there would be stale for whoever reaches the icon another way. **Read an Electron event's `@platform` before relying on it**: `mouse-enter` and `mouse-leave` do not exist on Linux, where the tooltip is the plain name. `createSystemTray` answers `undefined` only when the tray cannot be made (its icon is missing); on a Linux desktop that draws no tray the object exists and shows nowhere, and Electron does not say — there, starting Scia again is the way back to the window, and Linux stays untried (#13).
- **Main hears the engine; it does not ask it on a timer** (`engine/engine-events.ts`). Once the engine is ready, main follows its stream of changes (`GET /events`, with main's own token) for as long as Scia runs — not the page telling main through the bridge, which would add a member to it and depend on a page that may be hidden or reloading. It is the one thing main keeps open to the engine, and it has bounds of its own: `ENGINE_ANSWER_LIMIT_MS` for the answer to begin, and three of the engine's signs of life (`EVENTS_KEEP_ALIVE_MS` in `@scia/contracts`) for a stream that says nothing at all. The engine writes a comment when it has nothing to send, so an idle stream is never silent: **Node's `fetch` ends an answer after 300 s without a byte**, and a silent stream was cut every five minutes of an idle Scia. A stream that ends, is refused or goes silent is opened again after a wait, where the engine is by then; the loss is logged once and the return once; main closes the stream itself when Scia quits. What it sends is checked with the contract's schema, like any answer; an event main cannot read is logged and passed over.
- **A download that ends is said by the system when the person is not looking at the list** (`engine/ended-downloads.ts`, `ended-batch.ts`, `ended-notice.ts`, `window-state.ts`, `kept.ts`; the owner, 20 November 2026). Completed or failed, while the window is put away in the tray, minimised or not the window in use; never what had already ended when Scia started, never a pause or a removal. There is no switch for it in Settings for now: the system has one for every app.
  - Downloads that end within two seconds of the first share one notification, which counts them. Where the window is, is read when they are handed over, not when each ended: that is when the notification would show.
  - **The system draws it, with the system's limits**: Microsoft's documentation gives "up to 4 lines (combined)" under the title for the kind of notification Electron asks for; where it cuts, and the number itself, nobody has seen (#13). The body is composed within them — names first, what failed before what completed and marked in a mix, "and N more" for the rest, each name on one line (cut in the middle between characters as a person sees them, never through an emoji, its end and extension kept) — and what must not be lost comes within them: for the last download of a Scia put away in the tray, "Nothing else is downloading." and "Scia is still in the system tray.", which are true after a failure and with a paused download in the list.
  - **Every notification that can still be clicked is held** (`Kept`, twenty of them), not the last one: an earlier one is still on screen or in the system's list, and one nobody holds is collected with its click. It is let go on a click or a failure, never when the system says it closed — it says so as soon as it has shown it. A click opens the window through the one function both of Scia's notifications use, which does nothing once a quit has begun; the row there has "Open" and "Show in folder", and a program still asks for its second press.
  - **A minimised window is not `isVisible()` on Windows**: "put away" is shown once, and now neither shown nor minimised (`isPutAway`).
  - **"In front" is what the window believes** (`isInFront`, `MainWindow.isInFront`): on Windows `isFocused()` is not the system's answer. A Scia that was used and then left — minimised, or closed into the tray — is notified. A window shown while the system kept another window in use can believe it is focused — under script it did at some starts and not at others — and then counts as in front, and is silent until the person clicks into Scia and away, or minimises it, or closes it into the tray — shown and not minimised are asked before the focus: the plain case is a start during which they went back to their work. Seen under script, not by hand; what decides it, and how often a start by hand does it, is not known. Asking the system takes a native call, and an ADR (#62).
  - Its limit: a download that failed, was tried again and failed again before the engine sent a list showing it as anything else is said once (#55).
- **A notice a person needs once is shown once** (`engine/shown-notices.ts`, `notice-file.ts`): the first time the window hides, a notification says where Scia went. A notices file that cannot be read or written never stops anything; the notice is shown again.
- **What main loads by path ships in `dist/assets`**: `build.mjs` copies `assets/` beside `main.cjs` and fails without `tray.png`. The three PNGs (16, 24, 32 px) are rasterised from `assets/tray.svg`: redraw all of them together, never one.
- **Never tune a timeout against a warm start** — the first launch after an install is slow.

## User data

- Everything lives under `app.getPath('userData')`: `engine/` (the engine's state and the extension's token), `logs/`, `notices.json` (the notices already shown), `keys/` (the keys of the connected services, each sealed by the system). Nothing is written beside the executable.
- **Every run that is not the installed app passes `--user-data-dir=<scratch>`** (and `--port=<n>`), and main honours them: a dev build must never touch the real profile, the real Downloads folder or the installed app's port. A run that connects a service names a simulated one (`--alldebrid-api=http://127.0.0.1:<n>`): the engine takes an address on this computer and does not start with any other.

## Packaging

- `npm run dist` builds engine + renderer + main + preload, then electron-builder. `apps/desktop/package.json` stays at `0.0.0`; a release injects the version.
- **No native modules** without an ADR.
- **A zero exit code from a packager is not proof**: install the artefact, launch it on a scratch profile, read its log.
- `npm install` can leave `node_modules/electron/dist` empty while exiting 0. Symptom: missing `electron.exe`. Run `node node_modules/electron/install.js`.
